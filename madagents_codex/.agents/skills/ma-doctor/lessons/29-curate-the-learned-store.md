# 29 — Curate the learned store

> Edit before create, name by general class, consolidate near-duplicates and prune. And the learning write is its own step — it never degrades the user-facing answer.

A store that only adds and never consolidates drowns in its own duplicates (proliferation must be
paired with apoptosis). The discipline: edit the page you just used before spawning a new one,
broaden an existing category before adding a sub-file, create a new page only when nothing
matches; name an entry by its general *class*, never by today's specific question or error ("if
the name only makes sense for today's task, it's wrong"); periodically merge near-duplicate pages
into one with sub-sections. And keep the write a distinct step: folding "answer the user" and
"reflect on what to durably learn" into one call makes the reflection compete with the task —
answer first with the whole window on the answer, reflect at a natural break afterward.

**In a harness like this.** This is the consolidation discipline behind the wiki-lint pass and the
write-path skills: it stops the wiki ballooning into near-duplicate per-question pages, and
class-level naming keeps the stored knowledge general rather than overfit to one task. A
consultant's wiki write is separate from composing its return; the lead writes memory at a natural
break after the user has the answer, not mid-reasoning.

## Where the books say it

- **Hermes** — §04/§05. Edit before create, with class-level names (the skill-edit priority gradient; naming an entry after a PR number or error string is forbidden); consolidate by umbrella and prune, asking whether a human would write this as a few independent pages or one with sub-sections; and learning is its own step, never competing with the user's task for the model's attention.
- **Src-Analysis** — ch6. Consolidate and prune periodically — prune-as-you-grow; convert relative coordinates to absolute (here: an absolute `file:line` the page is read fresh at, never a value lifted off the page).
