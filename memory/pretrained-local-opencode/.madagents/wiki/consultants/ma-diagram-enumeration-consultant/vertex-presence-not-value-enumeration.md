# Enumeration keys off vertex PRESENCE, not coupling VALUE

Cites: `$MADGRAPH_INSTALL/madgraph/core/diagram_generation.py` + `base_objects.py` (v3.7.1). PROBE-VERIFIED (MG5_aMC v3.7.1, `import model sm`, the two runtime claims below). The count-vs-grep diagnostic here is generalized in `enumeration-topology-fingerprint.md`.

The recursive enumeration (`reduce_leglist` driven by `generate_diagrams`, see `reduce-leglist-recursion.md` / `generate-diagrams-algorithm.md`) builds diagrams from the model's INTERACTIONS — keyed by particle PDG-tuples, never by numerical coupling values. Three consequences, all anchored on `sm` 13 TeV `p p > w+ w- z` (read the per-qq̄ `Process has N diagrams`, the surviving-flavor-subprocess count, and the `Total:` roll-up fresh — drift-prone counts).

## 1. The enumeration input is PDG-tuples, never coupling values
- `reduce_leglist`'s only model inputs are `ref_dict_to0` / `ref_dict_to1` (`diagram_generation.py:976`, and built once in `generate_diagrams` :664-693) plus the integer `orders` budget. The ref dicts come from `model['interactions'].generate_ref_dict()` (`base_objects.py:1176-1177`).
- `InteractionList.generate_ref_dict` (`base_objects.py:983-999`) loops over EVERY interaction (skipping only UV/R2/UVCT loop counterterms) and calls `Interaction.generate_dict_entries`. That builder (`:861-891`) keys `ref_dict_to0[pdg_tuple] = [id]` and `ref_dict_to1[pdg_tuple] = [(pdg_part, id)]` purely from `tuple(sorted([p.get_pdg_code() for p in self['particles']]))` and `self['id']` — the interaction's particle PDG codes and integer id. It NEVER reads `self['couplings']` (the `GC_*` values) or `self['orders']`.
- An `Interaction` carries keys `id, particles, color, lorentz, couplings, orders` (`base_objects.py:624-625`); `couplings` defaults `{(0,0):'none'}` (:634). The enumeration consumes `particles` (→ ref dicts) and `orders` (→ `reduce_orders` integer budget), not `couplings`.
- All 23 `couplings` references in `diagram_generation.py` are coupling-ORDER (integer-power) handling — `present_couplings`/`coupling_orders`/`perturbation_couplings`/`WEIGHTED` (`reduce_orders` :1054-1088). None reads a numerical coupling value (`GC_*`, `['value']`, `parameter_dict` coupling entry).
- The ONLY param-card hook in `MultiProcess` is `use_numerical`/`optimize` (default `False`, `:1599`); when on it reads MASS values from `model['parameter_dict']` for a 1→N final-state-mass-≥-initial skip (`:1819-1828`) — never coupling values, and not in the standard `generate` path. So enumeration is coupling-value-blind in every path.

## 2. Coupling-value-zero leaves the diagram count UNCHANGED (contrast restriction removal)
- Setting an external coupling to zero in the param card (HVT `cq=0`, MSSM decoupled-μ) does NOT change what is enumerated: the vertex is still in `model['interactions']`, its PDG-tuple is still a ref-dict key, so the SAME diagrams are built. Only σ collapses at integration (the param card is read at launch, not at `generate` — `diagram_generation.py` never imports/reads a param card; the lone `param_card` mention :1582 is the `optimize` docstring).
- **This is the OPPOSITE of `restrict_default` removal.** `RestrictModel.restrict_model` (`models/import_ufo.py:2390`) DELETES a zeroed coupling — parameter + coupling + vertex are removed from the loaded model, so the PDG-tuple is no longer a ref-dict key and the diagram is never built (→ `NoDiagramException` for a lone empty process, or the silent multiparticle-member drop, see `multiprocess-crossing-mirror.md:44-50`). **Removed (vertex gone, fewer diagrams) ≠ value-zeroed (vertex present, same diagrams, σ=0).** The discriminator: count diagrams. Restriction removal changes the COUNT; a param-card zero does not.

## 3. Vertex-applicability is by leg-counting — a present vertex needn't enter a given final state
- `can_combine_to_1` (`base_objects.py:2253-2254`) and `can_combine_to_0` (`:2276-2277`) both gate on `tuple(sorted([leg.get('id') for leg in self])) in ref_dict_to1/to0`. A vertex enters a diagram ONLY if the sorted PDG-codes of the legs being clustered exactly match an interaction's key. A vertex whose particle content has no matching cluster among the available external legs (and their derivable internal lines) never fires.
- **WWWW quartic example:** the `sm` model HAS the WWWW quartic (`[W-,W-,W+,W+]`, `GC_35` — premise from ufo slice), but `p p > w+ w- z` has only 2 W external legs, so no 4-leg cluster can ever match the `(W,W,W,W)` key → the WWWW vertex contributes ZERO diagrams (matrix grep `GC_35` count 0 — a structural absence). "Vertex in the model" ≠ "vertex in this process." Count the external legs of that particle type. The applicable quartics here are γWWZ (`GC_57`) and WWZZ (`GC_36`) — grep their `GC_*` in `matrix1_orig.f` to confirm they fire.

## 4. gg → (colorless) prints "Trying" WITHOUT a "Process has N diagrams" line (zero-tree-diagram fingerprint)
- `generate_diagrams` logs `logger.info("Trying %s ")` near the start (`:636`), AFTER the conservation pre-checks pass, for every crossing it reaches.
- `"Process has %d diagrams"` is GUARDED: `if res and not returndiag:` (`:837-838`) — emitted ONLY when the recursion returned a non-empty `res`.
- So a process where `reduce_leglist` returns empty (no vertex-clustering path closes the diagram) prints `Trying ...` but NO `Process has ...` line. PROBE (`g g > w+ w- z QCD<=2 QED<=3`): `INFO: Trying process: g g > w+ w- z` followed immediately by `NoDiagramException : No amplitudes generated` — no `Process has` line. The colorless final state has no tree-level gg-initiated clustering path through the SM vertices (no ref-dict key clusters gg down).
- **This is the discriminator that rules out a "QCD/gluon-fusion" explanation** for a colorless-final-state count. In the inclusive `p p` expansion the gg member is enumerated (`Trying process: g g > w+ w- z` logged) but silently dropped (no `Process has` line, absent from the `Total:` roll-up) — the same silent zero-diagram-member drop documented in `multiprocess-crossing-mirror.md:44-50`, here for a LEG-TOPOLOGY (not removed-coupling) reason.

## Relation to the silent-drop / removed-coupling pages
- `multiprocess-crossing-mirror.md:44-50` documents the silent zero-diagram-member drop mechanism; its instance there is restrict_default REMOVAL (Yukawa vertex gone). This page adds the two non-removal reasons a member can be empty: (a) coupling VALUE zeroed does NOT make it empty (count unchanged), and (b) LEG-COUNTING — a present vertex with no matching leg cluster (gg colorless, WWWW with 2 W legs).
- Lead-side contrast: `removed-coupling-not-small` is the REMOVAL axis (vertex deleted → count changes); this page is the value-blind invariance (vertex present → count fixed). Same observable surface (Trying / Process-has lines, NoDiagramException, silent drop), opposite cause — always count diagrams to tell them apart.
