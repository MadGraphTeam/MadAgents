# MultiProcess.generate_multi_amplitudes (diagram_generation.py)

Cites: `$MADGRAPH_INSTALL/madgraph/core/diagram_generation.py` (v3.7.1). classmethod `def` :1664 (`@classmethod` decorator :1663).

Signature: `generate_multi_amplitudes(cls, process_definition, collect_mirror_procs=False, ignore_six_quark_processes=[], use_numerical=False, loop_filter=None, diagram_filter=False)`.

Docstring (:1670): "Make use of crossing symmetry for processes that FAIL diagram generation, but not for processes that SUCCEED ... Doing so will risk making it impossible to identify processes with identical amplitudes." Key asymmetry: failed crossings are skipped wholesale; successful crossings are reused only under conditions below.

## Coupling-order auto-detection
If `born_sq_orders` not set (:1683): `orders = find_optimal_process_orders(...)` (staticmethod :1928) — finds minimal WEIGHTED order giving diagrams; logs "Checking for minimal orders which gives processes." (:1982) and "Please specify coupling orders to bypass this step." (:1983). Then `check_expansion_orders()` (:1688).

### find_optimal_process_orders (:1928)
EARLY RETURNS (return `process_definition.get('orders')` unchanged, no search):
- any of `orders` / `overall_orders` set, or `NLO_mode=='virt'` (:1972-1975).
- single-incoming AND NOT `is_decay_chain` (a pure decay process) (:1978-1980).
Otherwise it runs an increasing-WEIGHTED search (docstring algorithm :1931-1962): starting guess from `get_minimum_WEIGHTED()` (:1986-1987); ceiling `max_WEIGHTED_order = (nlegs-2)*model.get_max_WEIGHTED()` (:1998-1999); loops `max_order_now` upward (:2013), generating with QCD gluons stripped from the FS and the WEIGHTED budget reduced by `nglue*order_hierarchy['QCD']` (:2042-2059), until diagrams appear; returns that order, else the ceiling. Per-iteration it lowers logger to WARNING to suppress per-crossing chatter (:2016-2017).

## Expansion loops
- Outer over IS id combinations `itertools.product(*isids)` (:1736); inner over FS `itertools.product(*fsids)` (:1764).
- FS double-counting removed via `red_fsidlist` keyed by sorted (id, polarization) tuples (:1762-1771).
- Longitudinal-photon polarization=0 stripped for massless legs; leg dropped if no polarization left (:1748-1757, :1788-1798).
- is/fs `is_tagged` (FKS) handled; tagging only one IS particle → `MadGraph5Error("Tagging only one initial-state particle is not allowed")` (:1739).
- `use_numerical` (1->N): skip if FS total mass >= IS mass (:1819-1828).

## Crossing / mirror / dedup bookkeeping
Trackers: `failed_procs`, `success_procs` (sorted-leg arrays), `non_permuted_procs` (raw id arrays, for mirror lookup), `permutations` (:1693-1700).
- `sorted_legs` = sorted outgoing-id list + permutation (:1801-1805).
- **six-quark skip**: if `ignore_six_quark_processes` and >=6 legs are those quarks → continue (:1808-1811).
- **failed crossing**: if `sorted_legs in failed_procs` → skip (:1815).
- **Mirror** (:1835-1853): only if `collect_mirror_procs and ninitial==2`. Build `mirror_proc` by swapping the two IS ids; if found in `non_permuted_procs`, set the EXISTING amp's `has_mirror_process=True` (:1849), log "Process ... added to mirror process ...", and `continue` (no new amplitude). So mirror = the IS-swapped variant folded into one kept amplitude.
- **Successful crossing reuse** (:1857-1885): only when process has NO required_s_channels, NO forbidden_onsh_s_channels, NO forbidden_s_channels, is NOT is_decay_chain, and NOT diagram_filter. If `sorted_legs in success_procs` (and not a loop amp), reuse via `cross_amplitude` (:1874) and continue. Loop amps explicitly excluded (`'loop_diagrams' in amplitudes[crossed]` → raise ValueError → falls through to fresh generation) (:1867).
- Otherwise: fresh `get_amplitude_from_proc(process)` then `generate_diagrams(diagram_filter=...)` (:1888-1892). InvalidCmd → append to failed_procs; success with diagrams → keep; success but empty diagrams AND `not result` → failed (:1893-1904).

## cross_amplitude (def :2118, @staticmethod :2117)
`copy.copy` the source amp, renumber legs via `perm_map = dict(zip(org_perm,new_perm))`, `renumber_legs` each diagram, `trim_diagrams()`, and RESET `has_mirror_process=False` (:2137) — a crossed amp does not inherit the mirror flag.

## Empty result
If no amplitudes: if exactly one failed proc and an `error` is in scope, re-raise that specific InvalidCmd (:1908-1909); else `NoDiagramException("No amplitudes generated from process %s. Please enter a valid process")` (:1911). `NoDiagramException(InvalidCmd)` defined :40.

## Silent zero-diagram-member drop in multiparticle expansion
A multiparticle/multi-id expansion produces one `process` per IS×FS id-combination, each generated fresh at :1888-1904. A member that yields ZERO diagrams is **dropped with no warning**, and the overall `generate` succeeds as long as ANY ONE member kept a nonzero amplitude. Mechanism (grounded for `generate p p > z h, (h > l+ l-)` with l± = e/μ/τ multiparticles, sm restrict_default, MG5_aMC v3.7.1):
- `generate_diagrams(returndiag=False)` logs `"Trying %s"` for EVERY member that reaches it (:636) — this is the per-combination `INFO: Trying process: h > e+ e- WEIGHTED<=2` chatter. After reduction, `failed_crossing = not res` (:708); for an empty member (e/μ Yukawa absent under restrict_default, `yme=ymm=0` → no HFF vertex) `res==[]` so `failed_crossing=True`. The `"Process has %d diagrams"` line is GUARDED by `if res and not returndiag:` (:837-838), so it is NOT emitted for an empty member — only the nonzero `h > ta+ ta-` prints its `Process has N diagrams` line. There is NO `logger.warning` on the empty path (the :1409/:1440 warnings are decay-chain scope mismatch, :933 is diagram_filter — none fire here). Anchored: most lepton-pair members silently empty, only `h > ta+ ta-` kept; only `P1_qq_zh_h_taptam` created.
- Caller: `result = amplitude.generate_diagrams(...)` (:1892) returns `not failed_crossing` (:852) = `False` for the empty member. `if amplitude.get('diagrams'):` (:1897) is False (`diagrams==[]` per :851), so the keep-branch (:1898-1901) is skipped; `elif not result:` (:1902) is True → `failed_procs.append(sorted_legs)` (:1904). So the empty member is RECORDED in `failed_procs` (which lets the :1815 failed-crossing check dedup a later identical empty crossing) but is NOT appended to `amplitudes` and emits no log line. User-observable: silently dropped.
- **NoDiagramException fires ONLY for the all-empty case**: `if not amplitudes:` (:1907) is the only gate. Because `h > ta+ ta-` kept one amplitude, `amplitudes` is non-empty and no exception is raised. The surviving result is exactly the `h > ta+ ta-` subprocess written alone — anchored σ bit-for-bit identical at fixed seed (0.02298 ± 1.806e-05 pb, 10k events) to `generate p p > z h, (h > ta+ ta-)`.
- **Contrast — explicit single-flavor `(h > e+ e-)` DOES raise** `NoDiagramException`: the decay ProcessDefinition expands to ONE member, which is empty, so `not amplitudes` (:1907) is True → `NoDiagramException("No amplitudes generated from process Process: h > e+ e- WEIGHTED=2")` (:1911). The exception fires because there is no surviving multiparticle member to fall back on — not because single-flavor is special. (This propagates unguarded up through the nested decay-chain construction; see the decay-chain section below.)
- **Distinct from the decay-chain mismatch warning**: this silent drop (an EMPTY id-combination during expansion) is a different mechanism from the `"Decay without corresponding particle in core process found"` / `"Decay information for particle(s) … is discarded"` warnings at :1409/:1440, which fire for a comma-only sub-decay scope mismatch (a decaying particle absent from the core). The multiparticle expansion drop here is genuinely warning-less.
- **Canonical DY fingerprint — `generate p p > l+ l-` yields SAME-FLAVOR pairs only, LFV combos silently dropped, no separate `add process` needed.** Same :1897/:1904 drop path, but the "why empty" is ABSENT-VERTEX-IN-MODEL, not the zeroed-Yukawa of the `h>l+l-` case above. With l+ = {e+,mu+} (l- = {e-,mu-}) expanded by model-loader, the inner FS product (:1764) enumerates all 4 lepton-id combinations per parton IS pair; the cross-flavor members (e+ mu-, mu+ e-) have NO SM vertex connecting the two distinct-generation leptons to a neutral current (no LFV in `sm`), so `generate_diagrams` returns empty → `amplitude.get('diagrams')` is False at :1897 → recorded in `failed_procs` (:1904), NOT appended to `amplitudes`, no log. Same-flavor members (e+e-, mu+mu-) keep γ/Z s-channel diagrams. NO `add process` needed: one `generate` line's expansion covers both surviving flavors. **PARTIAL drop is silent — `NoDiagramException` (:1911) fires ONLY if the `if not amplitudes:` gate (:1907) sees the ALL-empty case**, which cannot happen here (same-flavor members survive). The surviving-list being same-flavor-only is DIRECT from the drop mechanism + the absence of an LFV vertex (l± multiparticle content itself is model-loader's premise). Contrast: a lone `generate p p > e+ mu-` (no multiparticle fallback) WOULD raise `NoDiagramException` at :1911, same as the explicit single-flavor `(h > e+ e-)` case above — the exception is about the all-empty gate, not about single-vs-multi.

## Canonical lone-process vertex-absence raise — `e+ e- > g g` (probe-confirmed)
Probe-confirmed (MG5_aMC v3.7.1, `import model sm`, `generate e+ e- > g g`): parser ACCEPTS the line and reaches enumeration — `INFO: Trying process: e+ e- > g g WEIGHTED<=4 @1` prints (:636) — but reduction yields zero diagrams (no ref-dict vertex tuple connects colorless leptons to colored gluons: color/vertex-absence zero). No `Process has N diagrams` line (guarded by `if res` :837-838). Lone process → no surviving multiparticle member → `if not amplitudes:` (:1907) True → `NoDiagramException("No amplitudes generated from process Process: e+ e- > g g WEIGHTED=4 @1. Please enter a valid process")` (:1911, message = `process_definition.nice_string()`). This is the sharpest demonstration of the parser-acceptance ≠ amplitude-existence split: syntax validates in `extract_process`; emptiness surfaces only in `generate_diagrams`. Contrast in `p p > g g`: no `e+ e- > g g` member exists at all (p multiparticle content has no leptons — model-loader premise), so nothing is even attempted; the DY/`h>l+l-` PARTIAL-drop cases above are the multiparticle-expansion analogue where SOME members survive.

## NoDiagramException in a decay-chain branch (asymmetry vs core)
A decay sub-process is constructed via a nested `DecayChainAmplitude(process, ...)` at `diagram_generation.py:1386-1389`, with NO try/except around it (verified: the :1377-1398 block has no exception handling). A decay ProcessDefinition routes through `generate_multi_amplitudes` (:1361), which raises `NoDiagramException` (:1911) when it yields zero amplitudes. That exception therefore propagates UNGUARDED up through the nested chain construction and aborts the ENTIRE decay-chain generation — it is NOT folded into `failed_procs` the way a failed crossing at the core level is (:1893-1904). Asymmetry to cache: at the CORE/crossing level a dead process is absorbed (failed_procs) and may still leave other crossings; at the DECAY-LEG level a dead decay kills the whole chain with a hard `NoDiagramException`. (Whether the REPL `cmd` layer catches it for the user is the process-syntax slice; in-slice fact is that enumeration itself does not guard it.)

## Cautions
- Crossing reuse is DISABLED by required/forbidden s-channels, decay-chain, or diagram_filter (:1857-1860) — these break crossing symmetry, so each crossing is generated fresh. Don't assume crossings are reused when filters are present.
- `has_mirror_process` is only ever set when `collect_mirror_procs=True` AND ninitial==2; it stays False otherwise. The flag lives on the KEPT (first-seen) amplitude, not the skipped mirror.
- The single-error re-raise (:1908) only fires when exactly one crossing failed; with multiple failures the user gets the generic NoDiagramException, losing the specific reason.
- A decay leg given as a multiparticle ProcessDefinition (e.g. `t > b w+` where `w+` is part of a multiparticle, or several IS/FS expansions) routes through `generate_multi_amplitudes` (`diagram_generation.py:1361`) and `extend`s MULTIPLE amplitudes into ONE decay chain's `amplitudes` list (:1360). The inline `decay_ids` extraction (:1392) and `get_decay_ids` (:1517) both iterate over every amplitude in the chain, so all expanded decay variants of the same decaying particle share one decay-id entry. Don't assume one chain == one amplitude.
