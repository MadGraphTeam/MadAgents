**Common confusion — `/ X` ≠ forcing X as a propagator.** The `/ X` filter forbids X anywhere in diagrams (diagram filter); it does NOT force any particle to appear as an explicit resonant propagator. Example: `p p > z z, z > e+ e-, z > mu+ mu-` (comma sub-decays force both Z's as explicit propagators) vs `p p > z z / a a` (diagram filter removes photons but does not force Z propagators). Cross-ref: lead `process-line-scope-traps.md` §1.

## generate vs add process — state lifecycle (do_generate 4811, do_add 3232)
The two commands share `do_add`/`extract_process` but differ in *state management*:
- **`do_generate` (4811-4820) calls `clean_process()` FIRST** (4814) — `clean_process` (4791) RESETS `_curr_amps` (AmplitudeList, 4798), `_curr_proc_defs` (ProcessDefinitionList, 4800), `_curr_matrix_elements` (4802), `_generate_info=""` (4803), `_done_export=False` (4805), `_export_format=None` (4807). NOTE it does **NOT** reset `_export_dir` (source 4806-4807 only nulls `_export_format`). Then prepends `'process'` and calls `do_add`. So **`generate` WIPES all prior processes; `add process` APPENDS to them.** That is the whole functional difference — `generate X` ≡ `clean_process()` + `add process X`. (`clean_process` is also called on `import model`.)
- **`nb_proc` = `len([l for l in self.history if l.startswith(('generate','add process'))])`** (3291 decay / 3309 non-decay) — counts BOTH `generate` and `add process` history lines; passed as `proc_number` (the default `@N`). So the auto-assigned process id increments across the whole session history, not just within one `add process` chain. An explicit `@N` in the line overrides it (extract_process 4844).
- **`do_add` flag-strip set (3241-3254)**, all `args.remove()`d before `check_add`: `--no_warning=duplicate` (sets `warning_duplicate=False`), `--diagram_filter` (sets `diagram_filter=True`, passed to MultiProcess 3371), `--standalone` (sets `standalone_only=True`, bypasses the initial-state-mix check). `--optimize[=path]` is popped LATER (3264-3266, after check_add) not in this set.

## Amplitude-level duplicate detection + rollback (3374-3382)
After `MultiProcess` builds amplitudes (3368, enumeration slice's territory), `do_add` loops `for amp in myproc.get('amplitudes')` (3374):
- new amp → `_curr_amps.append(amp)`.
- amp ALREADY in `_curr_amps` AND `warning_duplicate` → `InvalidCmd("Duplicate process %s found. Please check your processes.")` (3378). This is a SECOND, distinct duplicate check from the initial-state-mix guard — it fires per-amplitude, comparing against already-accumulated amps, and is silenced by `--no_warning=duplicate`.
  - **LOAD-BEARING PRECONDITION (probe-confirmed v3.7.1, sm):** `amp not in self._curr_amps` is **dict equality** — `Amplitude` defines no `__eq__` (inherits PhysicsObject→dict; verified `'__eq__' not in Amplitude.__dict__`). Two amplitudes for the *same* process compare equal ONLY if their `process` key matches, and the `process` carries the `id` = proc_number = `@N`. Because `nb_proc` auto-increments (see above), a plain repeated `add process X` gets a *different* `id` → `process` keys differ → `amp not in` is True → **the duplicate raise does NOT fire**. Probes: `generate e+ e- > mu+ mu-` then `add process e+ e- > mu+ mu-` (no explicit `@N`) → **OK, n_amps=2, no raise**; but `generate e+ e- > mu+ mu- @1` then `add process e+ e- > mu+ mu- @1` → **`InvalidCmd: Duplicate process Process: e+ e- > mu+ mu- WEIGHTED<=4 @1 found`**. The only differing key between the two same-process amps is `process` (probe: `differing keys: ['process']`). So this check is effectively inert for ordinary duplicate lines and bites only when the two processes share an explicit `@N`.
- **Exception rollback (3380-3382)**: the whole `try` from 3339 is wrapped — ANY exception (including the duplicate one) does `self._curr_proc_defs.pop(-1)` (un-appends the procdef added at 3337) then re-raises. So a failed `add process` leaves `_curr_proc_defs` unchanged. NOTE the procdef is appended at 3337 BEFORE the try; the polarization/initial-state checks (3319-3332) run before 3337 so their raises do NOT trigger the pop.
- Final logging (3389-3398): "%i processes with %i diagrams generated" + a running "Total" across `_curr_amps`.
