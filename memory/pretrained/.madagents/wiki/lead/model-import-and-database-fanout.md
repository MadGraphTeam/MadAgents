# Model import and the model database — fan-out

Questions about *importing* a model, *where a model comes from* (bundled vs the online DB), *merging* models (`add model`), *which EW input scheme* a model fixes, and *how a restriction is selected at import*. This is the import-mechanics axis; complements `model-content-lifecycle.md` (what a model CONTAINS, declare→convert→prune→augment) and `model-variant-selection.md` (use the model already installed, verify with a `generate` probe). Pure router — MadGraph facts live in `../consultants/<name>/`; confirm one cited `file:line` before adopting a page as evidence.

## Owner map (route the sub-question)

- **Import orchestration** — session reset on `import model` (`clean_process` nulls `_curr_amps`/`_curr_proc_defs`/…), `name-restriction` split on the last `-`, absolute-path form (bare absolute path warns → use `./MODEL`), default-multiparticle build (`b` in `p`/`j` iff `b['mass']=='ZERO'` — mass-driven; `l±` = e/mu **excluding tau**, `vl` = ve/vm/vt **including** tau-nu), gauge & EW-scheme auto-switch → **`ma-model-loader-consultant`**.
- **`add model` plugin merge** — `do_add`→`add_model`→`usermod.UFOModel.add_model` (`models/usermod.py`); `BASE__PLUGIN` cache reused unless `--recreate`/`--output`; loop-model-as-plugin prohibited → **`ma-model-loader-consultant`** (`add-model-plugin-merge.md`). The min-merge *consumption* (hierarchy/expansion_order) is coupling-order + diagram-enumeration; the merge *site* is model-loader.
- **UFO file content** — which model dirs ship; external-vs-internal parameters (**MW is INTERNAL in `sm`** → the EW scheme is fixed by the external-parameter set, MW not settable in the param_card); `loop_sm` `lam` internal with `GC_30 ∝ lam·v`; `hgg_plugin` HIG/HIW orders + vertices; the `.pkl` model cache (per-gauge + `dec_` prefix); `coupling_orders.py` grammar → **`ma-ufo-consultant`** (`ufo-shipped-models-and-model-db.md`).
- **The ONLINE model database** — an absent-locally `import model X` (no hyphen) AUTO-downloads via `import_model_from_db` (wget+untar into `models/`); endpoint is `models_db.dat` from hardcoded UCL/INFN mirrors (`MG5aMC_WWW` env overrides); there is **NO `install <model>` command** — `do_install` covers downstream *tools*, not models. The curated `_online_model` dict is metadata (restriction-tag hints + `display modellist` seed), not a download trigger → **`ma-installation-consultant`** (`online-model-import-trigger.md`).
- **Restriction selection at import** — `import model NAME-TAG` loads `restrict_<TAG>.dat` (`-full` bypasses); what a given `restrict_*.dat` zeroes (e.g. `no_b_mass` zeroes MASS+YUKAWA PDG 5) → **`ma-restriction-consultant`**.
- **Coupling orders for effective/merged vertices** — selecting an effective vertex by explicit orders (`generate g g > h HIG=1 HIW=0 QED=0 QCD=0`), per-decay order independence in a chain, the `QED=99` idiom → **`ma-coupling-order-consultant`** (`effective-vertex-and-plugin-orders.md`).
- **Loop-capability / NLO model upgrade** — `sm`+`[QCD]` auto-upgrades to `loop_sm` (and `[QED]`→`loop_qcd_qed_sm`), in `loop_interface.validate_model`, NOT `do_import`; loop-capability is `perturbative_expansion>0` → **`ma-nlo-model-consultant`**; the bracket parse is nlo-syntax.
- **Model-inspection commands** — `display particles|interactions|multiparticles|parameters|modellist|coupling_order` (madgraph-prompt-only, model must be imported) → **`ma-interface-consultant`**.

## Doc-myth traps (a stale docstring / tutorial will hand you the wrong version)

Verify against source for THIS install — these are corrections source made to a plausible-sounding written claim:

- **"heft / 2HDM / EWdim6 / SMEFT are built-in."** FALSE on a minimal install — the shipped roster is `sm, loop_sm, MSSM_SLHA2, hgg_plugin, taudecay_UFO`; heft/2HDM/EWdim6 **and the EFT models (SMEFTsim / SMEFTatNLO / dim6top)** are online-DB, auto-fetched on import (test-suite copies under `tests/input_files/` are NOT import-visible). Always scan the actual `models/` dir for THIS install (ufo `ufo-shipped-models-and-model-db.md`). The effective ggH physics on a bundled install comes from `hgg_plugin`, not heft.
- **"`sm-full` loads a `restrict_full.dat`."** FALSE — no `restrict_full.dat` file exists; `full` is a reserved sentinel that sets `restrict_file=None` (`import_ufo.py:223-224`), bypassing `RestrictModel` so the raw UFO loads unrestricted. The *effect* (no simplifications) is right; the *mechanism* (a file load) is wrong. Diagnostic: a real restriction logs `Restrict model … with file restrict_*.dat`; `-full` emits no such line. → restriction / model-loader.
- **`add model` merge myths** (model-loader `add-model-plugin-merge.md`): particle-mass merge is *zero-yields-to-nonzero, else RAISE* — NOT "nonzero wins"; a near-duplicate vertex matching (sorted-PDG + lorentz + color + coupling ORDER) is **skipped with a warning**, NOT "both kept"; the collision-rename suffix is `__1`, not the plugin name.
- **"Set MW in the param_card."** In `sm`/`loop_sm` MW is an INTERNAL parameter — not written to the param_card, not overridable; the EW scheme is the α(MZ)-type set (aEWM1, Gf, MZ). Gμ-scheme-with-MW-input needs `loop_qcd_qed_sm_Gmu` (online).
- **"Run `install <model>`" / "manually place every downloaded model."** No model-install command exists; `import model X` auto-downloads any name resolvable in the live `models_db.dat`. Manual placement in `models/` is the fallback ONLY for a model absent from the DB.
- **"`display particles` shows PDG/mass/spin."** Bare `display particles` lists NAMES only; PDG/mass/spin come from the argument form `display particles <name>` (interface).
- **"`QED=99` raises the expansion_order ceiling."** It defeats the WEIGHTED auto-scan (`find_optimal_process_orders` early-return on non-empty orders); `check_expansion_orders` still re-caps per-order (coupling-order).
- **"sm handles `[QCD]` directly."** The upgrade to `loop_sm` is transparent but lives in `loop_interface`, not `do_import`; a non-sm-named tree model that fails the LoopModel gate is REJECTED (`… cannot handle loop processes`).
- **"`generate g g > h HIG=1 HIW=0 QED=0 QCD=0` works on hgg_plugin."** Only after `add model hgg_plugin` onto a QED-bearing base (the usual context). On *standalone* `import model hgg_plugin` the `QED=0` token InvalidCmd-aborts at `generate` time — and NOT because the model fails to declare QED (its `coupling_orders.py` DOES declare QED). The acceptance gate reads the **vertex-derived** order set (`get_coupling_orders`, `base_objects.py:1374` — orders appearing ON interactions), not the declared `CouplingOrder` names; standalone hgg_plugin has no QED-carrying vertex, so QED never enters the valid set. Merging onto a QED-bearing base introduces QED-carrying vertices → QED enters the set → the token parses. A token the loaded model's *vertices* don't carry hard-aborts; it is NOT silently stored as 0 (coupling-order `effective-vertex-and-plugin-orders.md`).

## Dispatch ordering

For a model-import/DB task, fan the owners the sub-questions implicate (breadth is cheap): model-loader (import + add model) + ufo (content + shipped roster) are the core pair; add installation whenever a not-locally-present model is named (auto-fetch), restriction whenever a `-TAG` restriction is in play, nlo-model whenever a bracket/loop-induced process rides on the import, coupling-order for effective/plugin-vertex selection. Confirm the shipped-vs-online status against the live `models/` dir before trusting any "built-in" claim.
