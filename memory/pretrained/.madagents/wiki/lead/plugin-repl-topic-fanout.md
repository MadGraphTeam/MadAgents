# Plugin-shipped-REPL topic fan-out (MadDM / MadDUMP / MadSTR)

## When it applies
Any task about a MadGraph **plugin that ships its own interactive REPL** — MadDM (`MadDM>`: dark-matter relic density, direct/indirect detection, spectral lines), MadDUMP, MadSTR, or a similar `--mode=<name>` extension. These plugins add their own `do_*` commands (a new command surface) on top of core MG5. A single such doc/task spans both **core MG5 mechanics** (verifiable against the installed MG5 source) and **plugin-internal commands** (only walkable when the plugin is installed under `PLUGIN/<name>`).

**First move: check what is installed** (mechanical, not a dispatch). `ls $MADGRAPH_INSTALL/PLUGIN/<name>` and `ls $MADGRAPH_INSTALL/bin/<name>*`; for a model-backed plugin also `ls models/*<model>*`. On a minimal install the plugin and its dedicated models are typically **absent** — then the plugin-internal half is a verified gap, and only the core-mechanics half can be grounded.

## Owner map — core mechanics the plugin leans on (all grounded against v3.7.1)
- **Install / fetch / launcher / version-enforce** → **ma-installation-consultant**. `<name>` is a registered plugin install target (`madgraph_interface.py:6484` `install_plugin=['maddm','maddump','MadSTR','cudacpp']`). `install <name>` fetches a **server tarball** (UCL/INFN package server, `--source`-steerable), **not** a github clone; `shutil.move`s it into `PLUGIN/<name>` (`:6809`) and — if the plugin defines `new_interface` — **auto-writes `bin/<name>.py`**, a wrapper that re-invokes `mg5_aMC … --mode=<name>` (`:6835-6858`). It does NOT copy the plugin's inner executable into `bin/`. Core enforces a plugin's `minimal_/maximal_mg5amcnlo_version` at **load** time (`misc.py:is_plugin_supported` ~2130-2167, called `bin/mg5_aMC:184-185`, `sys.exit` if unsupported); `do_install` reads the attr but does not version-block the install.
- **Plugin-loading + REPL + display/set surface** → **ma-interface-consultant**. The plugin's `new_interface` `Cmd` subclass **becomes** the REPL via `--mode=<name>` — the `<Name>>` prompt is just `--mode`, not a separate mechanism; the plugin's `do_*` methods are its new commands (`extended_cmd.py:911-927` sets `plugin_path=[MG5DIR/PLUGIN]`; `bin/mg5_aMC:169-187`). Core `_display_opts` (`madgraph_interface.py:2991-2994`) — `display particles|processes|diagrams|options|modellist` are all **core** (token is `modellist`; a plugin can extend `_display_opts`). Two `do_set`: MG5-prompt config/options (`madgraph_interface.py:8941`, sets `self.options`) vs the card-dialogue `set <param> <value>` (`common_run_interface.py:5868`, edits the card object). Launch-time `set mxd 500` / `set wy1 AUTO` is the card-dialogue form.
- **`define` base** → **ma-process-syntax-consultant**. Core `do_define` (`madgraph_interface.py:3527`) takes `args[0]` **verbatim** as a multiparticle label — there is NO sub-keyword dispatch. So `darkmatter` / `coannihilator` are **not** core keywords: in core MG5 `define darkmatter ~xd` would try to make a multiparticle literally named `darkmatter` (and in plain `sm`, `~xd` is undeclared → `InvalidCmd("No particle ~xd in model")`). The DM-candidate / coannihilator *semantics* are a **MadDM plugin override** of `do_define` (plugin-internal — see gap).
- **`/` diagram exclusion** → **ma-diagram-filter-consultant**. `generate … / z` forbids the Z on **internal propagators only** (s- AND t-channel; parse `madgraph_interface.py:5006-5019` → `forbidden_particles`, prune `diagram_generation.py:1016-1021`) — **not** external/final-state legs. Contrast `$ z` which KEEPS the Z diagram and only marks its s-channel propagator off-shell. For a relic-density annihilation `X X > SM SM` there is normally no external Z, so `/ z` cleanly removes Z-mediated diagrams; state the mechanism as internal-only. `/`-parsing is independent of the preceding tokens (so it works the same after a plugin observable keyword like `relic_density`).
- **`scan:` / `scanN:`** → **ma-param-card-consultant**. The locked/parallel-scan prefix is **`scanN:` for any integer N** (SAME N ⇒ lockstep single shared-index axis; DIFFERENT N or bare `scan:` ⇒ independent cartesian-product axes; `check_param_card.py:971,982,1002`). The RHS is `eval`'d (`:986`) — "any Python iterable" ≈ any expression that evals to something indexable. `AUTO`/`Auto`/`auto@NLO` is a **DECAY-only** width sentinel the card detects and hands to madwidth (`static_compute_widths`).
- **`[noborn=QCD]` loop-induced** (spectral-line γγ/γZ generation) → **ma-nlo-syntax-consultant**. `[noborn=QCD]` sets `HasBorn=False` / `LoopOption='noborn'` at parse and routes straight to `create_loop_induced` **before** the aMC@NLO squared-order / has-Born guard (`master_interface.py:225`), so a bare `[noborn=QCD]` never hits the `sqorders_types!='<='` reject. The `QCD` inside `[noborn=…]` is only the perturbation label (which coupling the loop is expanded in — a quark/αs loop for `a a` / `a z`), validated against the loop model's `perturbation_couplings`.
- **DMsimp model content** (particle names, couplings, masses) → **ma-ufo-consultant** + **ma-param-card-consultant** (+ ma-model-loader-consultant for import orchestration) — **only if a DMsimp model is installed**. Particle naming, the `DMINPUTS`/`MASS`/`DECAY` block parameters, `gVXd`/`gAXd`/generation-specific `gV*ij`, `MXd`/`MY1`/`WY1` are model-file facts to be read from the installed UFO, never from recall. Models auto-fetch on `import model <name>` (no install-command route; `models/import_ufo.py` DB fetch) or are dropped manually into `models/<name>/`.

## The plugin-internal GAP (owned by no consultant)
When the plugin is not installed, these are **verified gaps** — no roster consultant owns MadDM/plugin source, and there is nothing to walk. Do NOT cache them as fact; leave them as gaps/probe-candidates. Route the *core mechanics they ride on* per the owner map above, and to actually verify them, install the plugin first (`install <name>`) — then the plugin's own `do_*` are still unowned (a general-purpose walk of `PLUGIN/<name>` or a new dedicated slice would be needed).
- `define darkmatter` / `define coannihilator` **semantics** (DM-candidate / coannihilator selection) — a MadDM `do_define` override.
- Observable generation: `generate relic_density`, `add direct_detection`, `add indirect_detection`, `add indirect_spectral_features` (and the `generate` vs `add` "wipe vs append" distinction), the auto-fallback to loop-induced when no tree diagrams are found, DM-candidate auto-detection when `define darkmatter` is omitted.
- The `launch` menu switches (`relic`/`direct`/`indirect`/`spectral`/`nestscan`) and the plugin cards `maddm_card.dat` / `multinest_card.dat`.
- **`maddm_card.dat` parameter set** (names/options/defaults — e.g. `sigmav_method`, `indirect_flux_source_method`, `indirect_flux_earth_method`, `vave_indirect_cont` / `vave_indirect_line`, `profile`, `r_s`, `alpha`, `vave_direct`) and the **fast/precise presets** — plugin-owned; not in any core card slice. `nestscan`/**MultiNest has zero core hooks** (confirmed by grep over `madgraph/`: no `nestscan`/`multinest`/`pymultinest`/`nested_sampl` symbol) — the switch, `multinest_card.dat`, and the PyMultiNest dependency are entirely plugin-side; core scan machinery offers only grid iterators (`itertools.product` over `eval`'d lists), no sampler.
- **Output directory layout + result-file schema** — the `Indirect_tree_cont`/`Indirect_tree_line`/`Indirect_LI_cont`/`Indirect_LI_line` process dirs, the `Output_Indirect_*` symlinks under `output/run_NN/`, the combined `*_spectrum_*.dat` files, and the `MadDM_results.txt` observable variables (`OMEGA`, `x_f`, `sigmav(xf)`, `xsi`, `SigmaN_SI/SD_p/n`, per-channel `<sigma v>`, `Fermi ul`, J-factor, line cross sections) — plugin-authored; core `output`/`launch` produce none of these names.

## Doc-correction record (durable "the common write-up is wrong")
Instruction write-ups for these plugins commonly mis-state the core mechanics — the source-grounded corrections:
- `install <name>` fetches a **server tarball**, not a `git clone` of a github repo.
- The launcher is an **auto-generated `bin/<name>.py`** (`--mode` wrapper), not `cp PLUGIN/<name>/<name> bin/<name>` (the manual clone+copy works only because plugin recognition is `PLUGIN/<name>` directory-existence).
- `/ z` is **internal-propagator-only**, not "any leg" (external Z survives).
- The scan lock prefix is the general **`scanN:`**, not only `scan1:`; bare `scan:` on several params is an independent grid, not a lockstep scan. Same-length across a locked group is **not validated** — the group's axis length is taken from its *first* param (`check_param_card.py:999`), so a mismatched partner IndexErrors or is silently truncated.
- Scan-results **filename** `output/scan_run_NN.txt` is **not** the core pattern — core writes the summary to `Events/scan_<run_name>.txt` (launcher-set via `scanparamcardhandling`, `common_run_interface.py:7847`) plus per-point `run_NN_01/02/…` dirs and `Events/<run>/params.dat` (`check_param_card.py:1100`). Any `scan_run_NN.txt` a plugin shows is plugin-emitted, not inherited from the core launch slice.

## Dispatch ordering
1. **Mechanical install check first** (`ls PLUGIN/<name>`, `bin/<name>*`, `models/*`), never a dispatch.
2. **ma-installation-consultant** for the install/fetch/launcher/version mechanics (the whole "how do I get it running" half).
3. Then the **core-syntax slices** as the process line is built — interface (REPL/display/set), process-syntax (`define` base), diagram-filter (`/`), nlo-syntax (`[noborn]`), param-card (`scan`/`AUTO`), and ufo/param-card/model-loader for DMsimp model content **iff** the model is installed. These are largely parallel; cap the fan-out and drain each wave.
4. Flag the plugin-internal observable/menu/card commands as a **gap** (per above); do not attempt to answer them from core source.
