# Compiled-Fortran / emitted-file failure ≠ the matching Python slice

A build or run failure that shows up in generated Fortran tempts a mis-route to the Python slice whose *name* matches the symptom — `mc-integration` for anything about grids or helicity recycling. Two instances below are both **source-cleared** on the mc-integration side; route past it.

- **">132 characters / Line truncated" at compile.** Neither Fortran writer emits a >132-char line: `FortranWriter` wraps at **71** (`file_writers.py:201`), and the helicity-recycler preprocessor reflows *every* substituted sub-line at **72** (`hel_recycle.py:724`, `do_multiline` `char_limit=72`) — the injected `${helas_calls}`/`${jamp_lines}`/`${helicity_lines}` blocks and the scaffold alike. Worst emitted physical line ≈ <90 chars. So the recycler is **cleared** — it cannot be the locus. The genuine >132 line is a **writer-bypassing hardcoded / hand-`string.Template` `.f`/`.inc`** shipped verbatim under `Template/LO` (or `Template/NLO`) → **output slice** (`ma-output-consultant`), reproducible only with a many-coupling model actually compiled.
  - **Deactivation ≠ cure, and the off-switch has two forms that are NOT interchangeable.** `hel_recycling` as a **run_card** param (`banner.py:4454`, hidden, default True) is *runtime-deactivation only* — it cannot undo a *compile* error, because the offending `.f` is already emitted. The switch that changes what gets emitted is the **output-time flag** `output <dir> --hel_recycling=False`. Route "how do I turn off helicity recycling to dodge the compile error" to output (the output-time flag), never to the run_card slice. (Separately, spin-3/2-or-2 in the process auto-disables recycling at output, `madgraph_interface.py:9140-9142`.)
- **"SIGFPE during integration."** NOT the Python VEGAS grid-combiner. The unguarded divisions in `combine_grid.py:675/678` (`DiscreteSamplerDimension.update`, init branch, `sum_run/sum_ref` with `sum_ref=0` possible) are **Python** — they raise a `ZeroDivisionError` **traceback**, not a hardware SIGFPE, and only in init-mode with a reference channel whose total abs_weight is exactly 0 (reachability itself is a probe-candidate). A real SIGFPE is a **Fortran/OS FP-trap in the compiled madevent binary** — matrix-element evaluation or phase-space (`genps.f` → **phase-space slice**), with whether FP-trapping is even enabled decided by the build (`make_opts` compile flags → **installation slice**). The neighbouring `get_new_grid_for_var` divisions ARE epsilon-guarded (`:442` `+1e-99`, `:469` grid-size denom), reinforcing that the Python path is not the crash. Route "SIGFPE at integration" to phase-space + installation, not mc-integration.

**Unifying rule.** The Python file you can grep is not always the failure locus. When a failure lives in *emitted* or *compiled* code, route to the slice that owns the emitted artifact — output for verbatim `Template` files, phase-space/installation for the compiled binary — not the same-named Python slice whose code the reflow/guard already clears. Confirm the locus with a compile/run probe before naming the fix; both loci above are probe-candidates, not settleable from source alone.
