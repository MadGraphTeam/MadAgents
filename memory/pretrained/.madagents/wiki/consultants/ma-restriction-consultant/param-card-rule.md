# ParamCardRule — restriction's validity contract

`class ParamCardRule` at `$MADGRAPH_INSTALL/models/check_param_card.py:1121` (NOT under `madgraph/various/` — it lives in `models/`). `RestrictModel.default_setup` instantiates `self.rule_card = check_param_card.ParamCardRule()` (import_ufo.py:2381).

## Five rule lists (1134-1140)
- `zero` — params restricted to 0 (`add_zero`, 1145).
- `one` — params restricted to 1 (`add_one`, 1149).
- `identical` — params forced equal to another (`add_identical(block, code, code2)`, 1153).
- `opposite` — params forced to negative of another (`add_opposite`, 1157).
- `rule` — functional constraints from the MODEL itself, e.g. CKM unitarity (`add_rule(block, code, rule_expr)`, 1162).

## What populates them during restriction (import_ufo.py)
- `fix_parameter_values` → `add_zero` / `add_one` (3010, 3012) for each zero/one external param.
- `merge_iden_parameters` → `add_identical` (factor 1) / `add_opposite` (factor -1) (2844, 2847).

Restriction emits ONLY these four (`add_zero`/`add_one`/`add_identical`/`add_opposite`). Verified by grep: the only `rule_card.add_*` calls in import_ufo.py are at 2844/2847/3010/3012 — **`add_rule` is NEVER called by RestrictModel**. The `rule` (constraint) list is populated solely by `ParamCardRule.load_rule` parsing an XML `<rule>` element (check_param_card.py:1282) from a pre-existing serialized `param_card_rule.dat`. So model-supplied functional constraints (CKM unitarity etc.) ride in via a shipped/prior rule file, not generated by restriction.

## Where the rule_card lands on disk (boundary — output slice owns the write)
`export_v4.py:create_param_card` (9840-9863) writes `<dir>/param_card_rule.dat`, but gated on `if not hasattr(self.model, 'rule_card'): rule_card=False` (9844-9845). Only a model that went through `RestrictModel` carries a `rule_card` attribute → **`param_card_rule.dat` is written ONLY for restricted models**; an unrestricted (`-full`) model produces no rule file, so no zero/one/identical/opposite enforcement at card-check time. Consumed later at `common_run_interface.py:7040` (Source/MODEL copy) and `check_param_card.py:1842-1846`. The serialization call and consumers are output/param-card slices; recorded here as the operative→declared bridge becoming a physical file.

## Output and downstream use
`write_file` (1166) serialises to a `<file>...</file>` block with `<zero>/<one>/<identical>/<opposite>/<constraint>` sections → `param_card_rule.dat`. `load_rule` (1207) reads it back; `check_param_card` (1308) validates a param_card against the rules (optionally `modify`/`write_missing`).

## Significance for operative-vs-declared
The rule_card is the bridge between the restricted (operative) model and the param_card the user later edits. The restriction does NOT rewrite the param_card; instead it records THESE rules so that when the user edits the card, MadGraph can detect/forbid setting a restricted-to-zero param to nonzero, or breaking an identical/opposite link. Param-card content under the process directory and the actual check invocation are param-card slice; this page covers only what restriction WRITES into the rule object.

## Caution
The `rule` (constraint) list is read-back-only (loaded from a serialized `<rule>` element, never emitted by restriction — see above), distinct from the zero/one/identical/opposite that restriction generates. A user who edits a value that violates an identical/opposite rule established by their chosen restriction will be corrected/blocked at param-card-check time, which can surprise users who think any value is free. Conversely, since the rule file is only written for restricted models, an unrestricted (`-full`) model gives the user a fully free card with no merge/zero enforcement.
