# process_model & default multiparticles (v3.7.1)

`$MADGRAPH_INSTALL/madgraph/interface/madgraph_interface.py`.

## process_model (`:5953`)
Runs after model import (and after restriction has been applied — the operative model here is the RESTRICTED state). Three steps:
1. `self._particle_names` = names + antinames of `propagating` particles (for tab completion) (`:5958-5961`).
2. `self._couplings` = `misc.make_unique(...)` of all interaction `orders` keys (`:5963-5964`).
3. `self.add_default_multiparticles()` (`:5966`).

`pass_particles_name_in_mg_default()` (`madgraph/core/base_objects.py:1577`; called separately in do_import at `:5842` when `-modelname` absent) renames model particles to MG convention. It calls `load_default_name()` (separate static method at `:1760`) at `:1598`; `load_default_name` reads `$MADGRAPH_INSTALL/input/particles_name_default.txt` (file read at `:1766`), emitting "Change particles name to pass to MG5 convention" (`:1763`) and lowercasing each name (`:1776`). The file lists BOTH signs explicitly (`1 d`, `-1 d~`, … — both signs per PDG), so `default` keys on signed PDG. Conflicting name raises `MadGraph5Error` advising `-modelname` (text at `:1589-1593`, raised `:1595`).
- **MSSM Higgs forced rename** (`:1619-1622`): AFTER the generic name pass, if `model.get('name')=='mssm'` or startswith `'mssm-'`, particle PDG 25 is forcibly set `name='h1'`, `antiname='h1'`. This name test matches ONLY the literal `mssm` name — the modern installed model carries name `MSSM_SLHA2`, which does NOT match, so this rename is effectively dead for it. Probe (`import model MSSM_SLHA2; display particles`): lightest Higgs displayed as `h01`, NOT `h1` — confirming the rename did not fire. The block only fires for a model literally named `mssm`/`mssm-…` (the deprecated V4-era name; no such model is installed). Same probe confirmed the 3-arm `keep_external` detection: "Detect SLHA2 format. keeping restricted parameter in the param_card" fired for `MSSM_SLHA2` (via the 8-block-all or name arm).

## add_default_multiparticles (`:5998`)
1. **Prune stale defs** (`:6007-6016`): for each existing multiparticle key, drop it if any member PDG is absent from the new model's `particle_dict`, OR if the key now collides with a real particle name. Dropped keys go to `removed_multiparticles`.
2. **Load defaults** from `$MADGRAPH_INSTALL/input/multiparticles_default.txt` (`:6019-6038`): one `define` per non-comment line, only if the name isn't already defined. Case-folded to lower unless `case_sensitive`. Default file contents:
   ```
   p = g u c d s u~ c~ d~ s~
   j = g u c d s u~ c~ d~ s~
   l+ = e+ mu+      l- = e- mu-
   vl = ve vm vt    vl~ = ve~ vm~ vt~
   ```
   A `define` that fails (e.g. particle absent in restricted model) → `logger.warning('impossible to set default multiparticles ...')` and the history line is popped.
   - **Lepton/neutrino labels — the tau ASYMMETRY** (file `multiparticles_default.txt:17-20`, verbatim; `p`/`j` at `:15-16`): `l+ = e+ mu+` and `l- = e- mu-` — CHARGED lepton labels EXCLUDE tau (`ta+`/`ta-` are NOT in `l±`). But `vl = ve vm vt` and `vl~ = ve~ vm~ vt~` — the NEUTRINO label INCLUDES the tau-neutrino `vt`. So `l±` is 2-generation, `vl` is 3-generation. A user wanting tau in a charged-lepton label must `define` it explicitly (process-syntax slice). These four labels carry NO mass/flavour post-processing — only `p`/`j` get the b/photon adjustment below; `l±`/`vl`/`vl~` are the file literal verbatim.
3. **b-quark / flavour-scheme adjustment for `p` and `j`** (`:6042-6092`):
   - Looks up `b = self._curr_model.get_particle(5)`; if no PDG-5 particle, break.
   - If `5 in multi` and `b['mass'] != 'ZERO'` → remove 5 and -5 from p/j, `scheme = 4` (4-flavour) (`:6050-6054`).
   - Elif `b['mass'] == 'ZERO'` → append 5 and -5, `scheme = 5` (5-flavour) (`:6055-6058`).
   - **NOT a numeric mass cutoff/threshold.** The decision is an EXACT STRING equality `b['mass'] == 'ZERO'` (`:6051`, `:6055`) — `b['mass']` holds the mass PARAMETER-NAME string (e.g. `'mdl_MB'` for massive sm, the literal `'ZERO'` for a zeroed b), per the mass-as-param-name-string convention (conversion sets it). There is NO "m_b < X GeV" comparison anywhere; a b with a tiny-but-nonzero numeric mass parameter still counts as massive (name ≠ `'ZERO'`) and stays out of p/j. The scheme flips ONLY when restriction/ufo makes the mass attribute literally the string `'ZERO'`. (Whether a given restriction zeroes it → restriction/ufo slice.)
   - **Photon-in-jet**: if model `perturbation_couplings` includes `'QED'` → append 22 to p/j (`photon=True`); else remove 22 if present (`:6060-6068`).
   - Two MUTUALLY EXCLUSIVE log/history branches (`scheme` inits to `"old"` at `:6040`). Both messages are `logger.warning` (`:6073`, `:6084`) — WARNING-level, not info: a scheme flip to 4F/5F is surfaced loudly to the user (relevant when composing a matched sample, where the operative jet-flavour scheme must be known).
     - `if scheme in [4,5] and not photon` (`:6070-6081`): `optimize_order(multi)`, warns `"Pass the definition of 'j' and 'p' to <scheme> flavour scheme."`, rewrites history `define p = ...` / `define j = p`.
     - `if photon` (`:6083-6092`): warns `"...including the photon."` instead; the `and not photon` guard means the plain-scheme message is SUPPRESSED whenever the photon was added — only one of the two ever fires.
     - If neither (`scheme` stays `"old"` — e.g. no PDG-5 particle, `break` at `:6048`): no log, no p/j history rewrite, p/j keep the file-literal definition.
4. Log kept (`:6094-6098`) and removed (`:6100-6106`) multiparticles.
5. **Always** rebuild `all` tag from every model particle name+antiname via `self.do_define('all = ...')` (`:6108-6113`).

## Default `p`/`j` carry NO photon — the γγ/photon-PDF discriminator
The file literal (`$MADGRAPH_INSTALL/input/multiparticles_default.txt:15-16`) is `p = g u c d s u~ c~ d~ s~` and `j = g u c d s u~ c~ d~ s~` — **no `a` (photon)**. The photon (PDG 22) is appended to `p`/`j` ONLY when the model's `perturbation_couplings` contains `'QED'` (guard `:6061-6062`); otherwise 22 is removed if present (`:6066-6068`). Generic SM tree has no `'QED'` perturbation order, so its default `p`/`j` NEVER carry the photon.
- **Anchor** (`generate p p > w+ w- z` in default SM setup): prints `Defined multiparticle p = g u c d s u~ c~ d~ s~` — no `a`.
- **Consequence**: in a default setup, γq→X / γγ→X subprocesses contribute EXACTLY ZERO — they are never enumerated, because no initial-state photon is in `p`. A "photon-PDF / γγ-fusion" story for an observed default-setup σ is therefore WRONG unless the user has BOTH (a) explicitly redefined `p` to add the photon (`define p = g u c d s u~ c~ d~ s~ a`, a process-syntax-slice `define`) AND (b) switched to a photon-bearing (LUXqed-class) PDF. Either alone is insufficient: no `a` in `p` ⇒ no γ-initiated diagram regardless of PDF; a photon in `p` with a non-photon PDF ⇒ the channel is enumerated but draws zero photon luminosity.

## Custom UFO load by directory path (`import model /path` / `import model ./HVT`)
`import_model` (`$MADGRAPH_INSTALL/models/import_ufo.py:243`) resolves the model via `get_path_restrict` (`:204`) → `find_ufo_path` (`:69`), which accepts a directory path. Resolution arms:
- `./`/`../`-relative dir that exists → returned at `:75-76` (clean). **Recommended form: `import model ./HVT`.**
- installed `MG5DIR/models/<name>` → `:77-78`; `PYTHONPATH` dirs → `:79-85`.
- A bare path that `os.path.isdir` matches at `:86` (e.g. an absolute path) emits a warning "No model … found in default path. Did you mean 'import model ./…'" (`:87`) and, if the string contains `os.path.sep`, RAISES `UFOImportError` (`:89-90`). So a bare absolute path is NOT the clean route — prefer the `./`-prefixed (or installed-models-dir) form. (Path-resolution mechanics are in scope; the UFO directory's contents are ufo-slice.)

## Cautions
- The default `p`/`j` in the file are 4-flavour-looking (no b), but step 3 PROMOTES them to 5-flavour when the restricted model has a massless b (`mdl_MB`→ZERO). So the operative jet definition depends on the restriction's b-mass, decided AFTER the file is read. Don't assume p/j == the file literal.
- **Mechanism precision for default (massive-b) `sm`**: the file literal has no `5`, so the `5 in multi` active-removal arm (`:6050-6054`, `scheme=4`) is FALSE; and massive b makes the `elif b['mass']=='ZERO'` arm (`:6055`) FALSE too. So NEITHER arm fires — `scheme` STAYS `"old"`, and the `scheme in [4,5]` log block does NOT run: NO "Pass ... to 4 flavour scheme" message for default sm. Default sm is 4-flavour by FILE LITERAL + a no-op, not by an active `scheme=4` removal. The `scheme=4` removal path only fires when a 5-flavour `p`/`j` def was already present (persisting from a prior massless-b load) and a massive-b model is then loaded. The `scheme=5` ADD path (`sm-no_b_mass`, massless b) DOES fire and logs "Pass ... to 5 flavour scheme."
- **Name-split (`import model sm-no_b_mass`)**: `get_path_restrict` (`$MADGRAPH_INSTALL/models/import_ufo.py:210-220`) splits ONLY after `find_ufo_path('sm-no_b_mass')` raises `UFOImportError` — then `split('-')`, `model_name='-'.join(split[:-1])` (=`sm`), `restrict_name=split[-1]` (=`no_b_mass`) → `restrict_no_b_mass.dat`. Bare `import model sm` takes the `else` arm (`:225-229`): find succeeds, `restrict_default.dat` auto-applied. `-full` suffix (`:223`) bypasses restriction entirely. (Whether that restrict file zeroes `mdl_MB` is restriction-slice; the split parse + which file is chosen is mine.)
  - **File-content evidence** (`$MADGRAPH_INSTALL/models/sm/restrict_no_b_mass.dat` vs `restrict_default.dat`, MASS+YUKAWA blocks): the ONLY diff is block line `5` — MB and ymb go nonzero → `0.0` (read both files at that block line to confirm). So the variant zeroes exactly the b mass and b Yukawa. The MECHANISM by which the restrict-card literal `0.0` becomes the `'ZERO'` mass-attribute STRING that step-3 `:6055` tests (external→internal zero-collapse) is restriction-slice; the file existence + which values it carries is verifiable here. This is what makes `sm-no_b_mass` the 5F (massless-b) partner of default massive-b `sm`.
  - **Suffix-split is GENERIC over any model** (`get_path_restrict` keys only on `find_ufo_path(model_name)` raising, then `split('-')`): `import model loop_sm-no_b_mass` splits identically → `model_name='loop_sm'`, `restrict_name='no_b_mass'` → `restrict_no_b_mass.dat` (both `loop_sm/restrict_no_b_mass.dat` and `sm/restrict_no_b_mass.dat` ship; loop_sm IS installed). Nothing sm-specific in the split.
  - **Where the loader RECORDS the restriction** (relevant to the NLO auto-upgrade): `import_model` bakes the suffix into the model NAME — `model["name"] += '-' + restrict_name` (`$MADGRAPH_INSTALL/models/import_ufo.py:256-257`). The `restrict_name` attribute is then DERIVED back from the name by stripping the base modelname (`base_objects.py:1208-1213`: `restriction = modelname[len(basename)+1:]`). So `sm-no_b_mass` carries `name='sm-no_b_mass'`, `restrict_name='no_b_mass'`.
  - **sm→loop_sm auto-upgrade preserves the suffix** — but the CONSTRUCTION of the upgraded name is NOT my slice (it's the loop/aMC@NLO interface, nlo-model/amcatnlo): `loop_interface.py:328` reads `model_name = self._curr_model.get('name')` (= `sm-no_b_mass`, suffix included), tests base via `model_name.split('-')[0]=='sm'` (`:331`), and issues `import model loop_%s%s % (add_on, model_name)` (`:352`) → `import model loop_sm-no_b_mass`. MY do_import/get_path_restrict then RESOLVES that constructed name (split → loop_sm + restrict_no_b_mass.dat). Two ends: interface builds the name, model-loader resolves it. Bare `generate ... [QCD]` on a non-loop model in the base madgraph_interface generate path instead RAISES "does not allow for loop computations" (`madgraph_interface.py:5281-5283`); the auto-load only happens through the loop/aMC@NLO interface.
- Multiparticle defaults populate against the RESTRICTED model — particles pruned by the restriction make their `define` lines fail with a warning rather than error.
- The photon is added to j/p only for models whose `perturbation_couplings` carry QED (i.e. QED-loop-capable models), not generic SM tree.
