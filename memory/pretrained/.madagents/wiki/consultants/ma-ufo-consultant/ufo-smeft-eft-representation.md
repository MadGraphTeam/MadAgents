# How a SMEFT model is represented as UFO content (v3.7.1)

## Roster caveat — EFT UFOs come and go; re-resolve presence AND every count per build
EFT models are NOT part of the fixed shipped set (only `sm`/`loop_sm`/`MSSM_SLHA2`/`taudecay_UFO`/`hgg_plugin` are reliably on disk — see `ufo-shipped-models-and-model-db.md`). `models/SMEFTatNLO/` and `models/dim6top_LO_UFO/` may or may not be present in a given build — **`ls $MADGRAPH_INSTALL/models/` before citing any `models/SMEFTatNLO/...:line`.** The durable, always-present SMEFTatNLO anchor on this install is the test fixture `$MADGRAPH_INSTALL/tests/input_files/SMEFTatNLO_running/` (a complete UFO: `coupling_orders.py`/`couplings.py`/`parameters.py`/`vertices.py`/`CT_*.py`/`restrict_{default,LO,NLO,NLO_no4q}.dat`) — source-walk SMEFTatNLO grammar there when `models/SMEFTatNLO/` is absent. SMEFTsim's own UFO is not on disk in any form here → its declaration values are a GAP. **Everything below is a read-recipe: resolve the line and read the value fresh. Every count, default, and lhacode is version- and config-dependent — none is cached as a number.**

### Durable structural corrections (mechanism, not the numbers — read each fresh)
- **`coupling_orders.py`**: SMEFTatNLO declares exactly three orders `NP`/`QCD`/`QED` — `NP(expansion_order=2, hierarchy=1)`, `QCD(...,perturbative_expansion=1)`, `QED` — no `NPcpv`/`NPprop` (read the exact args at the decls, near `coupling_orders.py:8-19`). QCD's `perturbative_expansion=1` is what makes it a LoopModel (§6).
- **`mueft` (Renor[1]) is restriction-overridden**: the raw `parameters.py` external default (`nature='external'`, `lhablock='Renor'`, `lhacode=[1]` — read the raw value at its decl) is OVERRIDDEN by every `restrict_*.dat` (default/LO/NLO/NLO_no4q each set a `1 <val> # mueft` line — read the value at `restrict_default.dat`'s Renor block), and `restrict_default.dat` auto-applies at `import model`. So the OPERATIVE default ≠ the raw `parameters.py` value; the operative-value layer is restriction/param-card slice. In-slice fact = the raw value; the override existence is the durable mechanism (instance of `ufo-loader-keys-on-value-strings-not-numbers.md`'s raw-vs-operative split).
- **Input scheme is (Gf, MZ, MW) all EXTERNAL** — the reverse of sm where MW is internal. `Gf` SMINPUTS[2], `MZ` MASS[23], `MW` MASS[24] are all `nature='external'`; `aEW`/`aEWM1` are INTERNAL (`aEW='ee**2/(4.*pi)'`, `aEWM1='1/aEW'` — read near `parameters.py:882-892`). So MW IS a param_card MASS-block entry in SMEFTatNLO (contrast `ufo-sm-ew-input-scheme.md`, where sm's MW is internal/underivable). Confirm the external/internal nature of each at its decl.
- **Four-fermion WCs default TINY, not 1**: bosonic/two-fermion WCs (`Lambda` DIM6[1], `cpG` DIM6[8], `ctp`/`ctZ`/`ctW` DIM62F, chromo-dipole `ctG` — note `ctG` is DIM62F not DIM6) default O(1); the DIM64F four-fermion WCs (`cQq83`, `cQq13`, …) default ~1e-10. Read each default at its `parameters.py` decl — do NOT assume all WCs default to 1.
- **Inert-vs-wired discriminator (a RULE, re-grep per model — do not cache the assignment)**: a WC is INERT iff referenced by ZERO `Coupling` objects (grep the WC name in `couplings.py`/`CT_couplings.py`; grepping `vertices.py` is always 0 because vertices reference GC_ names, so that is NOT the test). A WC is LO-ONLY iff it appears in `couplings.py` but NOT `CT_couplings.py`. (Example, re-verify per build: some coefficients like a pure-gluonic O_G coefficient or a specific 4-fermion scalar may be declared-but-inert; some LO-only WCs enter tree couplings but no counterterm. Re-grep — which are inert/LO-only drifts with model version.)

Concrete read targets (WHERE PRESENT): `models/SMEFTatNLO/` (NLO, loop-capable) and `models/dim6top_LO_UFO/` (LO); when `models/SMEFTatNLO/` is absent use `tests/input_files/SMEFTatNLO_running/` for the SMEFTatNLO side. EFT operators are NOT a new UFO file type — they reuse the ordinary `CouplingOrder` / `Parameter` / `Coupling` / `Lorentz` / `Vertex` machinery (`ufo-model-file-structure.md`). What makes a model SMEFT is a *convention layer* on top of those declarations. This page records that layer; the loader's generic consumption of each file is on the sibling pages.

## 1. coupling_orders.py — the NP/EFT order is just another CouplingOrder

The EFT power-counting order is declared exactly like QCD/QED. The two anchor models DISAGREE on naming and convention:

- **SMEFTatNLO** (`coupling_orders.py:9-20`): one order `NP(expansion_order=2, hierarchy=1)`; plus `QCD(expansion_order=99, hierarchy=2, perturbative_expansion=1)` and `QED(expansion_order=99, hierarchy=4)`.
- **dim6top_LO_UFO** (`coupling_orders.py:9-23`): TWO EFT orders `DIM6(expansion_order=99, hierarchy=1)` and `FCNC(expansion_order=99, hierarchy=1)`; plus standard `QCD(99,1)`, `QED(99,2)`. No `perturbative_expansion` anywhere.

Loader reads these onto the Model verbatim (`ufo-coupling-orders-and-propagators.md` — fires for tree models too). PROBE (when `models/dim6top_LO_UFO/` is present — re-probe, read the dicts fresh):
- dim6top loads as plain `Model` (no `perturbative_expansion` → not a LoopModel); the two EFT orders `DIM6`/`FCNC` land in `order_hierarchy`/`expansion_order` alongside `QCD`/`QED` (read the exact values fresh off `coupling_orders.py`).
- SMEFTatNLO raw `import_full_model` loads as `LoopModel`, `perturbation_couplings=['QCD']`; read `order_hierarchy` / `expansion_order` fresh off `coupling_orders.py`. The load-bearing structural fact (read it, don't cache the dict): NP's `expansion_order` is a small integer CAP (not the 99 sentinel QCD/QED carry), and that cap is what enables the one-insertion default (§ non-obvious #1). (`import_model('SMEFTatNLO')` returns a `RestrictModel` because `restrict_default.dat` auto-applies — restriction slice.) When `models/SMEFTatNLO/` is absent, re-probe against the test fixture.

**Non-obvious #1 — the NP `expansion_order=2` is a REAL cap, not the 99 sentinel.** SMEFTatNLO caps `NP` at 2. Combined with the NP=2-per-insertion convention (below), this means the model-wide default allows AT MOST ONE dim-6 insertion per amplitude (NP^2 = one operator). dim6top instead leaves `DIM6`/`FCNC` at 99 (uncapped) and relies on the per-process parser to constrain insertions. So "how many EFT insertions are allowed by default" is answered IN `coupling_orders.py` for SMEFTatNLO but NOT for dim6top. Per-process overrides (`NP<=1`, `NP==2`, `DIM6=1`) are coupling-order/process slice; the loader only supplies the model-wide caps these are checked against (`base_objects.py:3757 check_expansion_orders`, see orders page).

## 2. parameters.py — Wilson coefficients are external Parameters in EFT LHA blocks

Wilson coefficients are ordinary `nature='external'` `Parameter`s; what marks them as EFT is their `lhablock`. LHA blocks observed:
- **SMEFTatNLO**: WC blocks `DIM6` (purely-bosonic, e.g. `cpDC` lhacode 2, `cpWB`), `DIM62F` (two-fermion, e.g. `ctG` chromo-dipole lhacode 24 — note `ctG` is DIM62F, not DIM6), and the four-fermion class SPLIT across THREE blocks `DIM64F` / `DIM64F2L` / `DIM64F4L`. Plus standard `YUKAWA`, `LOOP`, `Renor`, `MASS`, `SMINPUTS`, `DECAY`. Count entries per block (`grep "lhablock = 'DIM6'"` etc. in `parameters.py`) for the tally; the block ROSTER, not the counts, is the durable fact.
- **dim6top_LO_UFO**: `DIM6` and `FCNC` carry the WCs (count entries per block); plus `MASS`/`SMINPUTS`/`YUKAWA`/`DECAY`.

**Non-obvious #2 — the EFT cutoff scale `Lambda` is itself an external Parameter, lhablock `DIM6` lhacode 1.** Both models declare `Lambda = Parameter(nature='external', value=..., lhablock='DIM6', lhacode=[1])` (read the default at SMEFTatNLO `parameters.py:46-52` / dim6top `parameters.py:20-26` — it is O(1 TeV), read fresh). It is a `param_card` entry, not a hardcoded constant. Bosonic/2-fermion Wilson coefficients default O(1) (four-fermion default tiny — see roster caveat). So out-of-the-box every non-4F operator is effectively "on" — a user who forgets to edit the card gets those operators active.

**The 1/Lambda^2 suppression lives in VALUE EXPRESSIONS, not the parameter declaration.** A WC `Parameter` is just `c=1`; the `1/Lambda**2` appears where the WC is consumed — either an internal parameter (`vev` rotations, e.g. SMEFTatNLO `parameters.py:801 '(cpDC*vev0**2)/(2.*Lambda**2)'`) or directly in a coupling value (next section).

## 3. couplings.py — the dim-6 coupling carries the NP order + a 1/Lambda^2 value

A dim-6 `Coupling` is an ordinary `Coupling(name, value, order)` whose (a) `value` string contains `WC/Lambda**2`, and (b) `order` dict carries the EFT order. Example (SMEFTatNLO `couplings.py:297-298`): `GC_..., value='-((ctG*G)/Lambda**2)', order={...}` (chromo-dipole: one `ctG`, one `1/Lambda**2`, one `G`).

**Non-obvious #3 — the two models count an EFT insertion DIFFERENTLY in the order dict.**
- **SMEFTatNLO**: every dim-6 coupling carries `'NP':2` — NEVER `'NP':1`. (`grep -oE "order = \{[^}]*\}" couplings.py | sort | uniq -c`: top entries all `{'NP':2,...}`; zero `'NP':1`.) One operator insertion = NP=2 in the bookkeeping. This is why `expansion_order NP=2` permits exactly one insertion.
- **dim6top**: every dim-6 coupling carries `'DIM6':1` or `'FCNC':1` — one insertion = order 1. (top entries `{'FCNC':1}`, `{'DIM6':1}`, ...).

So a user writing process constraints must know which convention the model uses: `NP<=2` (SMEFTatNLO) vs `DIM6<=1` (dim6top) both mean "one insertion." Do not assume `NP=1` is a valid single-insertion constraint for SMEFTatNLO — it is not (no coupling carries it).

**Non-obvious #3b — isolate EFT by NP order, NOT by QED=0. The Higgs-gluon (O_HG/cHG) dim-6 vertex carries QED≠0 in SMEFTatNLO.** A common myth: "O_HG modifies Hgg, so its coupling is pure QCD+NP with QED=0, letting QCD/QED orders isolate the EFT piece." FALSE for SMEFTatNLO. Source-walk (use `models/SMEFTatNLO/` when present, else the test fixture `tests/input_files/SMEFTatNLO_running/`): the physical `g g H` vertex maps to a coupling of form `value='(4*cpG*i*vev0)/Lambda**2'` with **`order` carrying `QED≥1` and QCD ABSENT** (example: `GC_336`, `couplings.py`, `order={'NP':2,'QED':1}` — read fresh, GC index drifts). To confirm the rule per build, grep the cpG couplings' order dicts (`grep -A2 "cpG" couplings.py | grep -oE "order = \{[^}]*\}"`): EVERY cpG (=O_HG) coupling carries `QED≥1` and `NP=2`. The QED order tracks Higgs/vev field insertions (the `vev0` factor carries QED weight in SMEFTatNLO's power-counting), NOT the number of gauge couplings you'd naively expect. Consequence: **the discriminator that isolates a dim-6 contribution is the `NP` order (every EFT coupling carries `NP=2`), never `QED=0`.** A process constraint that tries to select the Hgg-EFT amplitude by fixing `QED=0` will DROP it (it needs QED≥1); use `NP` (`NP<=2`/`NP==2`) instead (coupling-order/process slice owns the constraint). The "QED=0 vertices exist" claim is a SMEFTsim-convention claim (SMEFTsim absorbs vev differently) — UNVERIFIABLE here (SMEFTsim not on disk) and demonstrably does NOT transfer to SMEFTatNLO.

**Non-obvious #4 — dim6top has CONFIGURATION-DEPENDENT order dicts** (dim6top is an oscillating EFT model — verify `models/dim6top_LO_UFO/` present before citing). `couplings.py` contains literal conditionals on `configuration.norm_chromo_gs`, in two co-equal forms (grep `grep -c "norm_chromo_gs" couplings.py` for the tally; region near `couplings.py:2175-2206`): (a) `'QCD':2 if configuration.norm_chromo_gs else 1` and (b) `'QCD':1 if configuration.norm_chromo_gs else 0`. Both attach `{'DIM6':1,...}` or `{'FCNC':1,...}`; e.g. `order = {'FCNC':1,'QED':1, 'QCD':2 if configuration.norm_chromo_gs else 1}`. So `norm_chromo_gs=True` adds ONE power of `gs`/QCD to every chromo coupling, but the default power differs by coupling. Because this is evaluated at IMPORT TIME, the loaded order dict depends on the `configuration.py` flag — and the pickle cache (`py3_model.pkl`) is keyed by path+gauge, NOT by configuration flags. Editing `configuration.py` without invalidating the pickle is a stale-cache hazard (see Cautions).

## 4. configuration.py — model-author flags that gate EFT content at import

A FeynRules-emitted file (NOT a standard UFO file; imported by `parameters.py`/`couplings.py` directly). Toggling these adds/removes parameters and couplings at import time:
- **SMEFTatNLO** `configuration.py`: `bottomYukawa = False`. When True, `parameters.py:11-27` activates `ymb` (YUKAWA #5) AND the bottom-Yukawa operator coefficient `cbp` (DIM62F #18), and `couplings.py` activates the `*_bot` couplings (`GC_1842_bot`, etc.). So whole WCs appear/vanish with this flag.
- **dim6top** `configuration.py`: `norm_chromo_gs = False` (chromo-dipole gs normalization, affects QCD order — #3 above) and `mw_ew_input = False` (EW input scheme).

## 5. lorentz.py — EFT operators introduce high-multiplicity contact Lorentz structures

EFT vertices reuse `Lorentz` objects, but dim-6 operators generate Lorentz structures the SM does not have: many-point contact terms. SMEFTatNLO `lorentz.py` holds MANY more `Lorentz(...)` than sm (count both fresh: `grep -c "^.* = Lorentz(" lorentz.py` in each). The durable fingerprint is the ROSTER of high-point families, not their counts — grep the family names (`grep -oE "name = '[A-Z]+" lorentz.py | sort | uniq -c`): the presence of high-point families `FFVVV`, `FFVVS`, `FFFF` (four-fermion contact), `VVVVV`, `VSSSS` is the source-visible signature of dim-6 contact operators (sm has none of these). The structure DSL is unchanged (Gamma/Sigma/P etc.); only the multiplicity and combinations are new. The loader COPY-RAWs `all_lorentz` (`import_ufo.py:585`, see consumption page); ALOHA generates the Fortran for these structures (ALOHA slice).

## 6. SMEFTatNLO NLO files — CT_vertices.py + CT_couplings.py (loop model)

SMEFTatNLO is genuinely loop-capable (QCD `perturbative_expansion=1` → `perturbation_couplings={'QCD':1}` → LoopModel + CT path runs, `import_ufo.py:501`). It ships `CT_vertices.py` (count `CTVertex` entries and split by `type='R2'`/`type='UV'` with `grep -c` — read fresh, drifts with version) and `CT_couplings.py` (count `Coupling(` entries). It has NO `CT_parameters.py` (the `__init__.py:44-49` import is try/except-guarded and silently passes) and NO `add_NLO` method — so the loader's `self.ufomodel.add_NLO()` raises AttributeError, swallowed by `except Exception: pass`, and it reads the pre-generated `all_CTvertices` directly (`ufo-ct-vertex-loading.md` #1; here the silent-fail IS the normal path for this model).

**Non-obvious #5 — the EFT structure (NP=2, 1/Lambda^2) is RETAINED in the CT couplings.** R2/UV counterterms of dim-6 operators carry `'NP':2` and `1/Lambda**2` just like tree couplings (e.g. `CT_couplings.py:13 R2GC_1000_1 value='...G**2*sw0)/(144.*cw0*cmath.pi**2*Lambda**2)...' order={'NP':2,'QCD':2,'QED':1}`). The loop counterterm of a dim-6 operator is still a dim-6 object.

**Non-obvious #6 — the Laurent pole is encoded as a dict-valued coupling.** SMEFTatNLO uses BOTH coupling-value forms (the `Coupling.pole(x)` mechanism, `object_library.py:250-262`):
- `R2GC_*` couplings: plain STRING value → `pole(0)` = the string (finite R2), `pole(1)=pole(2)='ZERO'`.
- `UVGC_*` couplings: DICT value `{-1:'...'}` or `{0:'...'}` → `pole(x)` returns `value[-x]`, so `pole(1)=value[-1]` is the single-pole UV divergence. A large share of CT couplings are dict-valued (`grep -c "value = {" CT_couplings.py`).
- **NO `{-2:` (double-pole) keys exist** (`grep -c "{-2:" CT_couplings.py` should be 0) — consistent with the loader's `InvalidModel`-on-double-pole contract (`ufo-ct-vertex-loading.md`). The model author guarantees single-pole-max at the coupling level.

PROBE (raw `import_full_model('SMEFTatNLO')`, when the model is present — re-probe, counts drift with version): the loaded LoopModel carries CT interaction-type KEYS `R2`, `UVloop`, `UVloop1eps`, `UVmass`, `UVmass1eps` (re-probe for per-key counts). The `1eps` siblings are the single-pole pieces from the laurent unfold (CT page 3-axis split); NO `2eps` KEY appears (no double poles — the loader's InvalidModel-on-double-pole contract). The bare `UV` types from the file auto-classify to `UVloop`/`UVmass` by particle content (CT page #2).

**dim6top is NOT a loop model.** Its `coupling_orders.py` has no `perturbative_expansion`, so it loads as plain `Model` and the CT path never runs. Its `CT_couplings.py` exists but is EMPTY (header only, zero Coupling objects) and there is no `CT_vertices.py` content used — vestigial files for a LO model. `__init__.py` still tries to `import CT_vertices` (guarded). Probe-confirmed: dim6top loads as `Model`, not LoopModel.

## Gaps (not settleable from UFO source alone)
- The PHYSICS naming / Warsaw-basis identity of each WC (which `cXX` is which operator) is FeynRules/author territory, only hinted by texname — not the loader's concern, and physical-value choice is physics slice.
- WHETHER a given process actually truncates at the NP cap depends on the per-process order constraint the user types (coupling-order/process slice) interacting with the model `expansion_order` — the model file only sets the cap.
- HOW MadLoop consumes the R2/UV interactions (R2 vs UV diagram bookkeeping, the EPS/FIN expansion at code-gen) is nlo-model/madloop slice.
- Restriction (which WCs `restrict_*.dat` zeroes, the LO/NLO/no4q variants) is restriction slice — SMEFTatNLO ships `restrict_default/LO/NLO/NLO_no4q.dat`; dim6top ships none.

## Cautions (source-visible hazards)
- **NP-counting convention mismatch.** SMEFTatNLO: one insertion = `NP=2`; a `NP=1` constraint matches NOTHING (no coupling carries it). dim6top: one insertion = `DIM6=1`/`FCNC=1`. A constraint string copied between the two models is wrong.
- **SMEFTatNLO silently caps at one insertion by default** (`expansion_order NP=2` + NP=2-per-insertion). Linear vs quadratic EFT (NP^2 interference vs |dim6|^2) is governed by this cap and the per-process order — easy to get the wrong order of truncation without realizing the model-wide cap is already restricting.
- **Lambda and WC defaults leave every operator active out-of-the-box** (read `Lambda` and the WC defaults at their `parameters.py` decls — Lambda is O(1 TeV), WCs O(1)). A run that forgets to edit `param_card` is NOT the SM.
- **configuration.py flags change the LOADED model but are NOT in the pickle key.** Editing `bottomYukawa` (SMEFTatNLO) or `norm_chromo_gs`/`mw_ew_input` (dim6top) changes params/couplings/order-dicts at import, but `py3_model.pkl` is keyed by path+gauge only (`ufo-loader-gauge-and-pickle.md`). Stale-pickle hazard: delete `py3_model*.pkl` / `__pycache__` after editing `configuration.py` or the old config is silently reused.
- **Per-gauge pickle caveat applies to these models** (`gauge = [0,1]` in both `__init__.py`): a Feynman-gauge load uses `py3_model_Feynman.pkl`, distinct from the default-unitary `py3_model.pkl`. SMEFTatNLO additionally ships `py3_dec_model.pkl` (the `decay=True` pickle — decay-aware load).
