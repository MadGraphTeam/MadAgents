## Recent lessons (FIFO, max 5)
- pert-order-filter-doc-traps: a troubleshooting doc mischaracterized 3 things about [QCD] loop filtering. Corrections (all v3.7.1 source): (1) filter_loop_for_perturbative_orders (loop_diagram_generation.py:496-539) discards ANY loop whose loop-LINE particle isn't QCD-perturbating (is_perturbating single-order test, base_objects.py:388) — NOT "pentagon-specific"; no N-point predicate exists. Two distinct warnings: actual-drop :510-513 "...are discarded...not pure (QCD)-perturbation" ('+'-join, literal parens) vs order-guess heuristic :736-739 "...might be discarded..." (','-join). (2) Discarding does NOT break the [QCD] IR-pole check — dropped W/Z/γ/H loops belong to [QED], carry no QCD IR singularity; keeping them would be the inconsistency (INFERRED; pole bookkeeping = fks). (3) nlo_mixed_expansion (default True) is the SAME mechanism from the other side: it sets perturbation_couplings/orders (amcatnlo_interface.py:672-673, fks_base.py:371-374) that the filter consumes. Trigger: any claim that a loop filter is topology/pentagon-specific, or that dropping non-pure-perturbation loops breaks pole cancellation.
- precisionvirtual-inverted-fix: FKS_params.dat PrecisionVirtualAtRunTime (default at :36, read fresh) → BinothLHA.f:182 `tolerance` → sloopmatrix_thres PREC_ASKED = target accuracy MadLoop must reach (smaller ⇒ more DP→QP escalation). Pole check runs at tolerance*10 (10× looser, :346); -1d0 disables check + uses OLP default. Trigger: a doc says "INCREASE PrecisionVirtualAtRunTime for higher precision" — INVERTED; you DECREASE it (toward a smaller magnitude) to tighten. Direction-of-remedy right (tighten virtual precision), arithmetic sign wrong.
- exporter-finalize-not-inherited: cached "loop-induced forces a Collier-first MLReductionLib chain" from loop_exporters.py:264 as a general loop-induced fact; probe (g g > z [noborn=QCD] output) showed the Ninja-first default chain (override absent) — the override is in LoopProcessExporterFortranSA.finalize but LoopInducedExporterME.finalize (:3131) does NOT call super(), so the MadEvent path skips it. Trigger: any class-method behavior (esp. finalize/__init__) read on a base class. Correct behavior: check whether the concrete subclass overrides it AND calls super() before generalizing; probe the actual output path.
- dead-code-and-overridden-default-trap: the MadLoop layer has ≥4 traps where an authoritative-LOOKING default/guard/branch is actually unreachable or shadowed — DefaultParam() (MadLoopParamReader.f:239, dead after unconditional stop:233, divergent CTModeInit/CTLoopLibrary/OSThres NEVER govern); is_loop_induced (madevent_interface.py:7532, dead assigned-never-read AND backwards-named); change_electroweak_mode bypass_check=True (loop_base_objects.py:1487, EW-scheme guard dead); SA 7|6|1 override not inherited on MadEvent path. Trigger: about to cite a compiled-in default, a safety guard, or a branch variable as governing behavior. Correct behavior: prove reachability (no preceding unconditional stop/return; the var is READ not just assigned; the method is actually CALLED on this path) before citing — the live source is often elsewhere (the written .dat, the :7489 branch, the Python default_setup).
- signature-accepts-ignores-is-not-user-silent-noop: cached "diagram_filter is a no-op in the loop path; a user expecting it gets no effect" from the static fact that LoopAmplitude.generate_diagrams(:595) accepts but never uses diagram_filter. Probe (generate g g > h [QCD] --diagram_filter AND [noborn=QCD]) showed InvalidCmd: No particle --diagram_filter — a HARD parse ERROR, not silent no-op. The --diagram_filter extraction lives ONLY in base madgraph_interface.do_add:3247, bypassed for every [...] bracket (master_interface routes to amcatnlo/loop/loop-induced ifaces that don't strip it → token parsed as a particle). The silent-drop is reachable only via the Python API. Trigger: inferring user-facing behavior from a "function accepts arg X but ignores it" static fact. Correct behavior: an EARLIER layer (arg parser / interface router) may reject the flag before it ever reaches the ignoring function — probe the actual command, don't assume the ignore-path is reached.
