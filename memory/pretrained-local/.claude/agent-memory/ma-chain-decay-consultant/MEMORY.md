## Core operating principles
- Verify against source for THIS input every dispatch; adopt a scope-matching cached page per ma-wiki-as-evidence (sanity-check one cite), else walk source.
- TWO axes split nearly every decay-chain question. BINDING (which legs become decay mothers / which subdecays attach-leak-drop) = paren-scope × set-based pdg-match, decoupled from "it parsed/ran" → decay-binding-is-scope-times-match. VALUE (what gForceBW a present s-channel mother gets) = ONE lookup of its `onshell` via booldict `{None:0, True:1, False:2}` (read it directly — drifts); trace the last onshell writer → onshell-as-single-source. BOTH: read the topology fingerprint (diagram count / warning cardinality / subprocess suffix / decayBW lines), never count commas; confirm via decayBW.inc.
- onshell=True (→1): trim_diagrams flags the CORE leg (diagram identity + `decay` field), but the OPERATIVE write on the combined-ME s-channel mother is insert_decay (helas_objects.py:4386). Leg→wf ctor copies onshell only when False (:675-677), never True — so the two non-default values reach the wf by different routes. onshell=False (→2) is the `$`/diagram-filter path; defer value-2 triage + runtime gForceBW effect to bw-window/phase-space.
- The cascade `>` stays in extract_process (core/decay fragments); it never enters extract_decay_chain_process, which splits only on `,`/`(`/`)`.

- paren-clause-uses-commas-not-cascade: when writing MG5 decay-chain process commands with parenthesized sub-decays, sub-decays MUST be separated by commas, NOT cascading `>`. `extract_decay_chain_process` (madgraph_interface.py:5661) splits ONLY on `,`/`(`/`)` — the cascade `>` stays in `extract_process` and never enters the decay-chain parser.
