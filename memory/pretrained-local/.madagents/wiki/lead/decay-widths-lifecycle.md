# Decay widths — six-slice lifecycle fan-out

A width question fans across six slices along the value's lifecycle (declare → restore → store → compute → consume). The recurring shape is the `config-value-lifecycle-layers` playbook with a **sentinel twist** — `'auto'` is a stand-in *resolved* at a specific stage, and the resolution trigger has multiple entry points, so a width can silently stay `0.0` if the trigger never fired.

Sub-questions:
- **AUTO width COMPUTATION / `compute_widths` / channel enumeration** → `ma-madwidth-consultant` — `compute_widths`/`calculate_decay_widths`, `DecayParticle`/`DecayModel`/`Channel`, body_decay (fractional default registered at `madgraph_interface.py:10195` — read it there), FeynRules 2-body + MadEvent N>2 survey, QCD-scale zeroing of small colored partial widths (threshold in `madgraph_interface.py` — read there). **Three AUTO-detection paths** (`runtime-autowidth-detection-trigger.md`): bare-REPL `compute_widths`, the MadSpin wrapper, and the launch/card-edit `static_check_param_card` regex; any single `auto@NLO` line flips the WHOLE dispatch to `--nlo`. **Command-surface doc-myths** (`compute-widths-option-doc-myths`, `compute-widths-flow.md`): `--precision=X` is NOT a valid option → hard `InvalidCmd` (the option is `--precision_channel`, the MadEvent survey accuracy); `--body_decay` is value-branched at `madgraph_interface.py:10195` — a WHOLE number (`2`, `3`, `4`) is exhaustive up-to-N-body, only a FRACTIONAL value (the shipped default) takes the precision-loop branch (int part = body cap, frac part = convergence stop), so the default caps at its integer-part body count (read the default at `madgraph_interface.py:10195`), not "2+3-body"; compute_widths **writes** the DECAY block back but prints **no** BR table (read the rewritten card); needs **no** prior `generate` (operates on the model alone).
- **model-side width DECLARATION** → `ma-ufo-consultant` `ufo-width-declaration.md` — `particle.width` is a symbolic `Param` name-string; external width params carry `lhablock='DECAY'`; `decays.py` analytic `partial_widths` copied only under `import_full_model(decay=True)` (own pickle key `py3_dec_model.pkl`). Open cross-slice gap: whether those analytic widths are ever consumed vs recomputed (probe-backlog).
- **restriction-side AUTO RESTORE** → `ma-restriction-consultant` `autowidth-restore.md` — `modify_autowidth` sentinel (`log10(2N)`) survives every prune/merge; DECAY block categorically exempt from `detect_identical_parameters` merge. Dormant for all bundled models (none ship an `'auto'` DECAY value).
- **card STORAGE / lifecycle** → `ma-param-card-consultant` `width-representation-in-card.md` — total width is a `float` OR the string `'auto'` and the value-type itself is the AUTO flag (no boolean); BR sub-lines in side dict `Block.decay_table`; block keyed `'decay'` not `'width'`; `@NLO` NOT preserved on a read+write round-trip.
- **runtime CONSUMPTION in the BW window** → `ma-bw-window-consultant` `bw-onshell-test-cutbw.md` — zero-width and tiny-width are different consumption paths: a tiny positive width is floored to `prmass*small_width_treatment` (the `small_width_treatment` run_card default is LO-only — read it in the generated `run_card.dat`); an exactly-zero/negative width is never BW-treated. `small_width_treatment` does not rescue a literal zero.
- **CONSUMPTION at the MadSpin handoff** → `ma-madspin-interface-consultant` `madspin-width-handoff.md` — width arrives via the banner param_card only (AUTO must be resolved upstream); total width is the BR denominator (`br *= pwidth/totwidth`); bridge/onshell divisions unguarded → a `0.0` total width crashes `ZeroDivisionError`.
- **CONSUMPTION as the in-process chain-σ BR denominator** → `ma-phase-space-consultant` `bw-resonance-rate-normalization.md` — for a `generate`-line chain decay (`b b~ > h, (h > w+ w-)`), the param-card total width IS the BR denominator with NO explicit BR multiplication: it enters the gForceBW=1 resonance's BW propagator denominator (`iM·MDL_WH`, `matrix1_orig.f` `VVS1_3`/`FK_MDL_WH`) AND the set_peaks BW sampling (`props.inc` `PRWIDTH`) — the SAME `DECAY 25` value — so the on-resonance |BW|² integral ∝ 1/Γ_total gives σ ∝ Γ_partial/Γ_total. Nothing reconciles Γ_total against summed partials; **BR ≫ 1 is silently accepted**; the only width abort (`myamp.f:417-428`) is purely kinematic (bwcutoff window-fit) so a stale-narrow width never trips it. (chain-decay marks WHICH leg is the resonance via `onshell=True`→`gForceBW=1` but never reads the width — `../consultants/ma-chain-decay-consultant/decayBW-artefact.md`.)

## The stale-width-after-mass-edit trap

A failure mode distinct from the `'auto'`-stays-0.0 one above: the width is **non-zero but STALE** — consistent with the OLD mass, not the edited one. Canonical case: a heavy-Higgs setup edits `MASS 25 → 400` but leaves the shipped `DECAY 25` unchanged (the 125-GeV-Higgs total width — read the shipped value in `param_card.dat` / `restrict_default.dat`; correct at 400 is ≈27.2 GeV). MG5 emits **no warning** — there is no mass↔width consistency check anywhere (`static_check_param_card` only recomputes a DECAY line that literally says `auto`; `update_dependent` never rewrites a free-external width — `../consultants/ma-madwidth-consultant/compute-widths-flow.md` "Stale width after a MASS edit", `../consultants/ma-param-card-consultant/width-representation-in-card.md`). The stale total feeds the chain-σ BR denominator above → **σ is off by the factor Γ_correct/Γ_stale** (for a large mass edit this can be orders of magnitude), and the implied BR(partial/total) can silently exceed 1. The magnitude is entirely setup-specific — derive it from the actual stale-vs-correct widths, never carry a factor. *(Example for this one MH 25→400 setup — illustrative, do not reuse the numbers: the shipped 125-GeV width vs the ~27 GeV correct at 400 skews the chain σ by ~Γ_correct/Γ_stale and pushes the implied BR(H→WW) well above 1.)* **Fix = regenerate after the mass edit** (`compute_widths 25` issued AFTER `set MH 400`, `DECAY 25 Auto`, or `set WH Auto` — all converge on `do_compute_widths`, `madgraph_interface.py:9801`, reading current-card masses). This is a derived-quantity-staleness instance — see `derived-quantity-staleness.md`.

## Two more routing angles: which channels exist, and is the LO number physically adequate

- **"Will `compute_widths` include channel X (H→gg, H→γγ, H→Zγ)?"** → this is a **model-content** question, not a madwidth-mechanism one. The enumeration filters to `type=='base'` (tree/effective) interactions (`decay_objects.py:1591`), so a channel exists **iff** the loaded model ships a tree/effective vertex for it. Route to `ma-ufo-consultant` (`ufo-vertex-presence-vs-coupling-value.md`): in bundled `sm` there is **no** `g g H`/`a a H`/`Z a H` base vertex → those Higgs channels are absent (only the Yukawa H→bb̄/ττ/cc̄/tt̄ and gauge H→WW/ZZ enumerate). **Effective-model caution:** `heft` is **not installed** on this system; the shipped effective-Higgs model is **`hgg_plugin`**, which carries **both** ggH (`V_13`) **and** an Hγγ (`V_12`) base vertex — so a blanket "the effective model has no H→γγ" is wrong for what is actually installed. Any `heft`-specific content claim is **unverifiable from recall** — route to the installation slice (online-DB fetch) before asserting, never answer heft content from a doc/memory.
- **"Is the tree-level auto-width physically good enough / do I need an external width?"** → `ma-physics-consultant` (`tree-level-auto-width-validity.md`). LO auto-width is a *consistent* internal number, not a physical one: the `sm` Hbb Yukawa uses `ymb` (YUKAWA[5], NOT the pole mass MB — read both in the generated `param_card.dat`) but the tree total still omits loop-induced channels and misses QCD K-factors, so `compute_widths h` in `sm` overshoots the physical width (LHCHXSWG **4.100 MeV = 4.1×10⁻³ GeV**) severalfold. The "NLO mismatch is sub-percent" generalization is **wrong** — H→bb̄ QCD is +~20%, t→Wb is −~9%; sub-percent holds only for leptonic/EW-only decays. **Supply an external Γ** for the Higgs (always), top (prefer NLO 1.32 GeV), W/Z (measured), and any loop-dominated or precision decayer. The *internal-consistency* exception: for MadSpin/chain-σ where the SAME tree-level model supplies both numerator and denominator, the LO total is the RIGHT denominator (keeps Γ_partial/Γ_total ≤ 1) even though it is not the physical width — hand-setting a smaller physical width there re-triggers BR>1.

Dispatch ordering: for "compute the width" → madwidth → param-card (AUTO write-back). For "why did my width come out 0 / get ignored" walk the lifecycle, asking at each stage which dropped the resolution (usually: the `'auto'` sentinel was never resolved because the compute trigger didn't fire → a literal `0.0` reaches the BW window / MadSpin BR denominator). For "I edited a mass and the chain σ is wildly off / BR>1" → it is the stale-width-after-mass-edit trap: madwidth (regenerate) + phase-space (the BR-denominator mechanism).
