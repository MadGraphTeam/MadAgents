# Loop-matrix runtime driver + PS-point restoration

The Fortran that the compiled MadLoop actually executes per phase-space point. Templates:
- `$MADGRAPH_INSTALL/madgraph/iolibs/template_files/loop_optimized/loop_matrix_standalone.inc` (optimized mode, the default — line numbers below) and the un-optimized `loop/loop_matrix_standalone.inc` (parallel structure, different line numbers).
- `$MADGRAPH_INSTALL/madgraph/iolibs/template_files/loop/improve_ps.inc` — the PS-point restoration routines.

These templates are emitted into `<PROC>/SubProcesses/<P*>/loop_matrix.f` and `improve_ps.f` by `$MADGRAPH_INSTALL/madgraph/loop/loop_exporters.py` (`write_improve_ps` :1242 — emits QP-only via `real_format=real_mp_format`/`mp_prefix='MP_'`/`mp_specifier='_16'` :1253-1257; `loop_matrix_standalone.inc` read at :2966 optimized / :1628 default; `improve_ps.f` written :2123 optimized / :1125 default). This page owns the RUNTIME SEMANTICS (what the driver computes per point); the EMISSION machinery (exporter mechanics, file layout) is nlo-export-adjacent — cited only as the boundary. Closes the loop with ./madloop-params-runtime-knobs.md (which documents the param DEFAULTS but not how they drive the runtime eval) and ./loop-check-infrastructure.md (the Python check layer that drives the standalone driver from outside).

## Per-point evaluation flow (optimized driver)
1. **PS-point restoration** (:862-865): `IF (ImprovePSPoint.ge.0) CALL <prefix>IMPROVE_PS_POINT_PRECISION(PS)` — runs at the FRONT of every ME eval to make the input point exactly on-shell + 4-momentum-conserving before reduction. `ImprovePSPoint<0` ⇒ skipped (use the point as given). This is why the `improve_ps.f` artifact exists.
2. **N_EVALS planning** (`SET_N_EVALS` :2193-2212): `CTMODERUN.LE.-1` ⇒ `N_DP_EVALS = 2 + NRotations_DP`, `N_QP_EVALS = 2 + NRotations_QP`. The constant **2 = the two loop-direction (CTMode) evals** (original + reversed propagator order); `NRotations_*` add Lorentz-rotated re-evals ON TOP. `CTMODERUN.GE.0` (fixed mode) ⇒ exactly 1 eval each, no stability comparison. Hardcoded cap: `N_*_EVALS>20 ⇒ stop 1` "Increase hardcoded maxstabilitylength." **`NRotations_DP`/`NRotations_QP` defaults** are read at banner.py MadLoopParam :6151-6152 / MadLoopParams.dat :88/:91 — with the shipped default the runtime stability test does ONLY the 2 loop-direction evals and no extra Lorentz rotations. The "2 ROTATE_PS rotations" below are a baked-in CAPABILITY (max), NOT the default behavior; rotation 1/2 fire only if a user raises NRotations_DP/QP above the default. (Caveat: the TIR-cache-clearing call SET_AUTOMATIC_CACHE_CLEARING(.FALSE.) force-zeros NRotations back to 0 with a warning, :2635-2640.)
3. **The evaluation-method dispatch** (the `EVAL_DONE(2..4)` block, ~:1627-1670): a single point is evaluated in multiple "methods":
   - method (CTMode `BASIC_CT_MODE`): `BASIC_CT_MODE=4` if `DOING_QP_EVALS` and the lib has QP, else `=1` (:1620-1624). Mode 1/4 = DP/QP original propagator order.
   - **loop-direction test** `EVAL_DONE(2)` (:1627+): `CTMODE = BASIC_CT_MODE+1` (mode 2 or 5 = reversed propagator order) — gated on `LOOPLIBS_DIRECTEST(MLReductionLib(I_LIB))` (all current libs support it; a TIR lib that did not would just copy mode-1's answer, :1631-1648).
   - **Lorentz rotations** `EVAL_DONE(3)`/`EVAL_DONE(4)` (:1655-1666): fire only when `NRotations_DP/QP >= 1` / `>= 2` respectively; call `ROTATE_PS(PS,P,1)` / `ROTATE_PS(PS,P,2)`.
   - final un-rotated eval `ROTATE_PS(PS,P,0)` (:1668, rotation 0 = identity).
4. **Stability decision** (:1746-1758, DP branch): `CALL COMPUTE_ACCURACY(DP_RES,N_DP_EVAL,ACC,ANS)`; a floating-point exception in reduction hard-sets `ACC=1.0` (:1749-1753). Then `IF (MAXVAL(ACC).GE.MLSTABTHRES)` ⇒ **advance to next reduction library** `I_LIB=I_LIB+1`; if the `MLReductionLib` chain is exhausted (`I_LIB>NLOOPLIB` or next entry 0) AND `QP_TOOLS_AVAILABLE`, switch to the first QP-capable tool `INDEX_QP_TOOLS(1)` and reset FPE flags (:1755-1762). This is the RUNTIME realization of: (a) the Ninja-first `MLReductionLib` chain fall-through, and (b) the DP→QP escalation — both documented only at the param level in ./madloop-params-runtime-knobs.md.

So: `MLStabThres` is the per-point accuracy gate; `CTModeRun=-1` enables the auto multi-eval stability machinery; `NRotations_DP/QP` add rotated cross-checks; the `MLReductionLib` chain is walked in order, falling to QP only when DP is exhausted.

## What MadLoop returns + reports per point — the H/T/U return code (authoritative docs at `loop_matrix_standalone.inc` SLOOPMATRIX_THRES :2879-2918, U-func at `$MADGRAPH_INSTALL/Template/loop_material/StandAlone/SubProcesses/MadLoopCommons.inc:263-327`)
The public per-point entry `<prefix>SLOOPMATRIX_THRES(P,ANS,PREC_ASKED,PREC_FOUND,RET_CODE)` (:2867) returns `ANS(3)`=(finite,1eps,2eps), `PREC_FOUND`=estimated relative accuracy (−1 if no stab test ran), and the integer `RET_CODE = 100*H + 10*T + U` (composition formula stated at :418, `common/...ACC/ACCURACY,RET_CODE_H,RET_CODE_T,RET_CODE_U` at :424; `SLOOPMATRIXHEL_THRES` :2806 is the single-helicity variant). The three digits are the canonical MadLoop stability verdict:
- **H (hundreds) = stability CLASS** (docs :2881-2891): `1`=stability unknown (e.g. CTModeRun≠−1, or init/checkphase — no test performed); `2`=**SPS** Stable PS point, no rescue needed; `3`=**UPS** Unstable PS point, stability rescue (QP) was necessary AND successful; `4`=**EPS** Exceptional PS point, rescue attempted but unsuccessful (result not trustworthy). These SPS/UPS/EPS labels are the SAME three classes the Python `check_matrix_element_stability` counts (./loop-check-infrastructure.md), here emitted by the compiled runtime itself. H set inline: `=2`(:1830, DP stable), `=3`(:1685, QP rescue OK), `=4`(:1690/:1789, EPS), `=1`(:1835/:1851, unknown/checkphase).
- **T (tens) = precision / init phase** (docs :2893-2900): `1`=DP computation only; `2`=QP was used for this point; `3`=init phase, DP only; `4`=init phase, QP used. Set at :1845-1853: `T=2` iff `MP_DONE_ONCE`, else `1`; then `+2` (→3/4) if `CHECKPHASE.OR..NOT.HELDOUBLECHECKED` (init/filtering phase) — and in that init case H is force-reset to 1, ACCURACY to −1 (the stability verdict is meaningless during filtering).
- **U (units) = which reduction TOOL achieved stability** (`SET_RET_CODE_U(MLRed,DOING_QP,STABLE)`, MadLoopCommons.inc:263; docs :268-287): `0`=not stable; `1`=CutTools DP; `2`=PJFry++; `3`=IREGI; `4`=Golem95; `5`=Samurai; `6`=Ninja DP; `7`=COLLIER; `8`=Ninja QP; `9`=CutTools QP. Note **only CutTools(→9) and Ninja(→8) have a QP code** — `SET_RET_CODE_U` `STOP`s `'Only CutTools and Ninja can use quardruple precision'` (:319) if any other lib is passed with `DOING_QP=.TRUE.`, matching the [1,6]-only QP-recovery restriction in the Python classifier and ./loop-check-infrastructure.md. `STABLE=.FALSE.` ⇒ U=0 unconditionally (:307).

## Unstable-point runtime messages (`loop_matrix_standalone.inc`, EPS branches)
When the chain is exhausted and the point is classed EPS (H=4), the driver writes to stdout (NOT just a return code):
- `##W03 WARNING An unstable PS point was detected.` (:1696 QP-exhausted path, :1793 no-QP path). The no-QP-capable-tool path additionally writes `##W03 WARNING No quadruple precision will be used.` (:1794).
- If a floating-point exception drove the instability: `## The last QP reduction was deemed unstable because a floating point exception was encountered.` (:1698) / `## The last DP reduction ...` (:1796). An FPE hard-sets every `ACC(I)=1.0d0` (:1679/:1750) so the point is forced unstable.
- Full per-point dump (only for the first 10 EPS points): DP + QP accuracies (per split order if `NSQUAREDSO≠1`), best estimate `(fin,1eps,2eps)`, every finite DP and QP evaluation, `MU_R`, and all external momenta (:1700-1724). **`NEPS` counter gates verbosity**: `IF(NEPS.LE.10)` prints the dump; `IF(NEPS.EQ.10)` prints `Further output of the details of these unstable PS points will now be suppressed.` (:1726-1728/:1822-1824). So a run with many EPS points reports only the first 10 in detail — do NOT infer the EPS count from the number of detailed dumps in the log.
- Separately, the per-split-order instability warning `##W03 WARNING Contribution N is unstable.` (:1307) fires when a particular squared-order contribution's stability flag `S(...)` is false while copying the loop result.

## JAMP self-consistency cross-check (color-flow path only — `## if(ComputeColorFlows)`, block :1552-1600)
A SEPARATE MadLoop self-check, distinct from the stability test: when emitted with `ComputeColorFlows` (the loop-color-flow path, ./loop-color-basis.md — used by the loop-induced MadEvent export) AND at runtime `DIRECT_ME_COMPUTATION.AND.ME_COMPUTATION_FROM_JAMP` (the gate, :1553), the driver recomputes Born/finite/single-pole/double-pole from the color JAMPs and compares against the direct result. Header `=== JAMP double-checking test ===` (:1555); per K it prints `Direct result`, `Computed from JAMPS`, `Relative diff.`; if the relative diff exceeds `JAMP_DOUBLECHECK_THRES` (compile-time PARAMETER, :26 — read the magnitude fresh) it `STOP 'Consistency cross-check of JAMPS failed.'` (:1595). This is a hard abort, not a soft warning — a development/validation cross-check gated behind the dual flags. **NOT on any default path**: source labels it "a JAMP consistency check turned off by default" (:22); NEITHER default flag config sets both true — standard output `DIRECT=.TRUE./JAMP=.FALSE.` (:37-38), loop-induced output `DIRECT=.FALSE./JAMP=.TRUE.` (:33-35) — so the `.AND.` is `.FALSE.` in both, and the block fires only if a developer hand-edits BOTH flags to `.TRUE.`.

## ROTATE_PS rotations (improve_ps.inc)
Three discrete rotations (NOT continuous angles); only 0/1/2 are defined (improve_ps.inc `ROTATE_PS`):
- rotation 0 = identity (xp=x,yp=y,zp=z).
- rotation 1 = (xp=z, yp=-x, zp=-y).
- rotation 2 = (xp=-z, yp=y, zp=x).
Energy component P(0) always preserved. The QP variant `MP_ROTATE_PS` additionally sets the global `MP_DONE=.FALSE.` so the QP momentum cache is recomputed for the rotated point. NOTE: these are the RUNTIME stability rotations (driven by NRotations_DP/QP). They are DISTINCT from the 6 Python-side check rotations (z-axis π/2, π/4, boost, axis perms) in process_checks.py (./loop-check-infrastructure.md :1411-1439) — the runtime driver has only 2 non-trivial rotations baked in.

## improve_ps.inc — the PS-point restoration (always QP)
`IMPROVE_PS_POINT_PRECISION(P)` (DP wrapper) copies P into QP, calls the QP `MP_IMPROVE_PS_POINT_PRECISION`, copies back. **The restoration ALWAYS runs in quadruple precision** even when the ME eval is DP — `write_improve_ps` emits ONLY the QP version (`real_format=real_mp_format`, `mp_prefix='MP_'`, `mp_specifier='_16'`, exporter :1253-1257; docstring :1242-1245). Non-obvious: precision restoration is QP-only regardless of the eval precision.

Flow inside the QP routine:
1. `IS_PHYSICAL(NEWP,WARNED)` sanity-checks the input: 4-momentum conservation to `THRES_FOURMOM=1d-6` (relative) and on-shellness of every leg to `THRES_ONSHELL=1d-2` (relative). Fails ⇒ `ERRCODE=1`, "ERROR:: The input PS point is not precise enough." and the point is left unmodified (warning + WRITE_MOM dump).
2. Restoration method by `ImprovePSPoint`: **`==1` ⇒ PSMC method** (`PSMC_IMPROVE_PS_POINT_PRECISION`); **`==2` or `<=0` ⇒ ORIG method** (`ORIG_IMPROVE_PS_POINT_PRECISION`, the V.H. method). On failure the OTHER method is tried as a rescue (:swap at the ERRCODE block); both failing ⇒ point left unmodified + warning.
3. `IS_CLOSE(P,NEWP,WARNED)` guard: the shifted point is rejected if `sum|P-NEWP| / sum|P| > THRS_CLOSE=1d-2` ("The improved PS point is too far from the original one") — the restoration must be a small deformation, not a new point.
4. Warnings are suppressed after 20 ("Further warnings ... will now be supressed").

### ORIG (V.H.) method — `ORIG_IMPROVE_PS_POINT_PRECISION`
Closed-form 2→N restoration. **Preconditions** (else ERRCODE 100-500): exactly 2 initial-state particles (NINITIAL==2, else 100); both IS momenta along z (transverse < THRS_TEST=1d-15, else 200); both IS particles massless (else 300); all energies positive (else 400+I). Then: shifts all FS particles exactly on-shell (recomputes pz from E,px,py,m), then solves a Mathematica-derived 4-eqn system (energy + z-momentum conservation + on-shellness of the two IS) for energy/z shifts to the two IS momenta. Works only for the standard massless-collinear-IS hadron/lepton-collider kinematics.

### PSMC method — `PSMC_IMPROVE_PS_POINT_PRECISION`
More general: enforces exact space-like momentum conservation by fixing the last particle's 3-momentum, then Newton-solves (`FINDX`/`FUNCT`, MAXITERATIONS=8, CONVERGED=1d-26) for a global 3-momentum rescaling factor `x` that makes total energy conserved (tries seeds 1.0, 1.1, 0.9, NAPPROXZEROS=3), scaling particle 1 by `x**2` (others by `x`) so the Newton derivative is non-vanishing in the all-massless case; then recomputes all energies on-shell; CONSISTENCY_THRES=1d-25 on residual energy non-conservation. Does NOT require massless/collinear IS, so it is the fallback for the ORIG method's restricted kinematics.

## Cautions
- `ImprovePSPoint` default is `2` (./madloop-params-runtime-knobs.md) ⇒ ORIG (V.H.) method first. For a process whose IS is NOT two massless back-to-back partons (e.g. massive-IS or non-collinear setups), the ORIG method hits its preconditions and ERRCODEs out, silently falling back to PSMC — restoration still happens but via the slower Newton path. (caution, not a runtime claim)
- `IS_CLOSE` can REJECT a restored point (leaving the original imprecise one) if the deformation exceeds 1% — for a genuinely far-off input the "improved" point is discarded and the ME is computed on the unrestored point. The restoration is best-effort, not guaranteed. (caution)
- `CTMODERUN.GE.0` (a user pinning a fixed reduction mode) DISABLES the entire multi-eval stability machinery: N_EVALS=1, no loop-direction test, no rotations, no MLStabThres gate, no DP→QP escalation. A fixed CTModeRun trades stability detection for speed. (caution, static-verified from SET_N_EVALS :2200). **Boundary precision:** the FULL auto-stability mode requires `CTMODERUN.EQ.-1` *specifically* — not merely `LE.-1`. SET_N_EVALS uses `LE.-1` (so -1/-2/-3 all get N_EVALS>1), but the stability-collection block (:1603) and the CTMODE init (:839 `CTMODERUN.NE.-1`⇒`CTMODE=CTMODERUN`) gate on `EQ.-1`. The header comment (:154-157) is authoritative: `CTMODERUN=-1`=full stability, `-2`=pin to rotation-1 only, `-3`=pin to rotation-2 only, `>=0`=pin CTMODE to that exact value (1 eval). The MadLoopParams.dat comment confirms: "MLStabThres is used only when CTModeRun is negative" and "[Lorentz-rotation tuning] is only relevant when running MadLoop with CTModeRun=-1." So the page's GE.0-vs-LE.-1 binary is a simplification; -2/-3 are intermediate single-purpose modes.
- The 2 runtime ROTATE_PS rotations are a DIFFERENT, smaller set than the 6 Python check-infra rotations — do not assume the runtime stability test rotates the way the `do_check stability` command does. (caution)
