# SM restrict_*.dat files

`ls $MADGRAPH_INSTALL/models/sm/restrict_*.dat` → ckm, c_mass, default, lepton_masses, no_b_mass, no_masses, no_tau_mass, no_widths, zeromass_ckm (9 files). A restrict file IS a param_card (header "PARAM_CARD AUTOMATICALY GENERATED BY THE UFO"); restriction reads its numeric values to decide what to prune/merge.

## restrict_default.dat (the implicit default restriction)
Blocks: SMINPUTS (aEWM1, Gf, aS), MASS, DECAY, Wolfenstein, YUKAWA — read numeric values in the active `restrict_default.dat`.
Key defaults already baked in:
- MASS: MC=0, Me(11)=0, MM(13)=0 → charm, electron, muon MASSLESS by default (the zeros are the pruning-determining fact). MB, MT, MTA, MZ, MH kept nonzero — read magnitudes in the active card.
- DECAY: tau width=0; top, Z, W, H carry nonzero widths (read magnitudes in the active card).
- Wolfenstein lamWS=AWS=rhoWS=etaWS=0 → CKM is the IDENTITY by default (no quark-generation mixing). This is why a default-SM process has no CKM-suppressed transitions.
- YUKAWA: ymc=0, yme=0, ymm=0 (track the zero masses); ymb, ymt, ymtau kept nonzero (read magnitudes in the active card).

## Variants (diff vs default)
- `no_b_mass`: `diff restrict_no_b_mass.dat restrict_default.dat` = EXACTLY two lines — MASS block PDG 5 `→0` (MB) and YUKAWA block PDG 5 `→0` (ymb). Everything else identical to default (MC=Me=MM=0, MTA nonzero, diagonal CKM). "5-flavour scheme" is the downstream *consequence*, not something the card states. See "no_b_mass: mass-vs-Yukawa" below for what each zero does.
- `no_masses`: MB→0, MTA→0 (and ymb→0, ymtau→0) — b and tau massless (charm/e/mu already 0 in default).
- `no_tau_mass`: tau mass→0.
- `c_mass`: charm mass restored (un-zeroes MC) — name means "with c mass", opposite of the default-massless-charm.
- `lepton_masses`: restores lepton masses.
- `ckm`: Wolfenstein → physical CKM (lamWS/AWS/rhoWS/etaWS set nonzero — read magnitudes in `restrict_ckm.dat`). Enables quark mixing.
- `zeromass_ckm`: CKM mixing AND light-quark masses zeroed.
- `no_widths`: ALL DECAY widths→0 AND also shifts MH, ymb, ymt to different values (read `restrict_no_widths.dat`).

## no_b_mass: mass-vs-Yukawa (two zeros, two different effects)
The card sets BOTH `MB=0` and `ymb=0`; they act through different RestrictModel paths:
- **`MB=0` (mass, external, MASS block):** a zero external → converted to internal fixed 0 (`detect_special_parameters`/`fix_parameter_values`). Removes NO vertex — mass is not a coupling; it only makes the b propagator massless and is the value the 5-flavour multiparticle logic keys on (that logic is model-loader's — see seam below).
- **`ymb=0` (b Yukawa, external, YUKAWA block):** drives internal `yb = (ymb*sqrt(2))/vev` (parameters.py:349-353) to 0. `yb` is consumed by EXACTLY two couplings (grep `\byb\b` couplings.py → only GC_82, GC_83):
  - GC_82 `-(yb/sqrt(2))` → **V_77** `[b~, b, G0]` (FFS2) — removed.
  - GC_83 `-(i*yb/sqrt(2))` → **V_78** `[b~, b, H]` (FFS4) — removed.
  No mixed t-b coupling uses `yb` (no `ymt*ymb` term in couplings.py); the charged-current W-t-b and any G+-t-b vertices are gauge/top-Yukawa driven and SURVIVE. So `sm-no_b_mass` prunes precisely the H-b-b and G0-b-b Yukawa vertices — parallel to the e/μ case (removed-coupling-not-small.md), removed≠small.

### Doc-folklore debunk: "MB and ymb independent, so b b~ > h survives despite ymb=0" is WRONG
`ymb` (parameters.py:85, external YUKAWA) and `MB` (parameters.py:149, external MASS) ARE two distinct, independent externals — `ymb` appears ONLY in `yb` (parameters.py:352); no mixed `ymb*MB` term. That independence is TRUE. But the inference "so the Hbb vertex survives with MB≠0" is FALSE: the Hbb/G0bb COUPLING is `ymb`-driven (via `yb`), NOT `MB`-driven. Setting `ymb=0` → `yb=0` → GC (couplings.py:337 G0bb, 341 Hbb) = 0 → V_77/V_78 PRUNED (import_ufo.py `value==0`@~2549, `interactions.remove`@~2927). A nonzero `MB` only keeps the b PROPAGATOR massive — it does not supply an Hbb vertex. So `import model sm-no_b_mass; generate b b~ > h` → NoDiagramException (probe documented in the "bbH is a LOUD NoDiagramException" section below), NOT a nonzero result. To get a massless-b WITH live Hbb, keep `MB=0` but restore `ymb≠0` (custom card, recipe in loop_sm section) — MB alone cannot do it.

### Consequence: bbH is a LOUD NoDiagramException for the lone process (source+probe confirmed)
Because `ymb→0` prunes V_78 `[b~, b, H]`, the only diagram of `b b~ > h` is gone. Parse/generate probe (MG5_aMC v3.7.1, no launch):
- `import model sm-no_b_mass; generate b b~ > h` → `NoDiagramException: No amplitudes generated from process Process: b b~ > h WEIGHTED=2 @1`.
- `import model sm; generate b b~ > h` → `Process has 1 diagrams` (default sm keeps MB/ymb nonzero → V_78 present).
So for the LONE process the failure is LOUD (an exception, not a silent zero). The SILENT variant — `b b~ > h` as one subprocess among others in a multiparticle process, where MG5 drops just that subprocess and proceeds — is a SEPARATE, still-unconfirmed probe-candidate (mechanism expected identical to the e/μ multiparticle drop in removed-coupling-not-small.md, but not yet probe-verified for bbH).

### Seam: 5-flavour p/j membership is model-loader's, not restriction's
The restriction only sets `MB=0`. Whether a massless b then joins the `p`/`j` multiparticle definitions (5-flavour scheme) is decided by `add_default_multiparticles` AFTER restriction — model-loader slice. Restriction's contribution to the seam is solely the operative `MB=0`; do not author the membership logic here.

## loop_sm mirror (verified v3.7.1) + massless-b-WITH-Yukawa recipe
`loop_sm/restrict_no_b_mass.dat` `diff` vs `loop_sm/restrict_default.dat` = EXACTLY two value changes: MASS PDG 5 `→0` (MB) and YUKAWA PDG 5 `→0` (ymb). (A third diff line is trailing whitespace on `DECAY 25`.) NO `DECAY 5` line in either card — b has no width param in (loop_)sm, so "zero the WB width" is a non-event; the card neither sets nor zeros WB.
loop_sm coupling/vertex chain (names differ from plain sm, mechanism identical):
- `yb = (ymb*cmath.sqrt(2))/v` (parameters.py:385-388). `ymb` external YUKAWA (parameters.py:121-126); `MB` external MASS (parameters.py:177+) — **fully independent externals, no mixed `ymb*MB` term anywhere** (`grep ymb` → only the `yb` definition).
- `yb` used in EXACTLY two couplings (`grep '\byb\b' couplings.py`): `GC_33 = -(i*yb)/sqrt(2)` (QED:1) and `GC_1082 = -(yb/sqrt(2))` (QED:1).
- `GC_33` → `V_27` `[b~, b, H]` (FFS1, vertices.py:204); `GC_1082` → `V_1077` `[b~, b, G0]` (FFS2, vertices.py:652). ymb=0 → yb=0 → both couplings 0 → both vertices PRUNED (import_ufo.py `if value==0`@2550, `self['interactions'].remove`@2927). Parallel to sm GC_82/GC_83 → V_77/V_78.

**Custom "massless b WITH nonzero b-Yukawa" recipe is mechanically sound at the restriction level.** Copy `restrict_no_b_mass.dat`, keep `MASS 5 = 0` but restore `YUKAWA 5` to a physical nonzero, save as `restrict_<tag>.dat`, `import model loop_sm-<tag>`. Because MB and ymb are independent externals, a nonzero ymb keeps yb≠0 → GC_33/GC_1082 survive → V_27/V_1077 (Hbb, G0bb) are NOT pruned, while MB=0 makes the b propagator massless. Restriction treats the two zeros independently (mass path = detect_special/fix_parameter_values; Yukawa path = zero-coupling pruning) — no code ties them.
Restriction-level hazards to avoid when hand-authoring: (1) do NOT set the kept ymb to a literal `0` or `1` (triggers zero/one external→internal conversion) — use a physical nonzero; (2) avoid setting ymb to a value that exactly equals another kept same-block (YUKAWA) param (ymt, ymtau) or `detect_identical_parameters` (import_ufo.py:2709) would merge them — pick a value colliding with nothing. Runtime/NLO physics consequences of MB=0 with yb≠0 (5F yb-scheme, mass-renorm/CT in loop_sm, rate correctness) are physics/probe, OUT of my slice.

## Magic-value escapes (read with restrict-model-pipeline.md)
A restrict card cannot use literal 0 or 1 for a value it wants to KEEP as a free external param (0/1 trigger zero/one conversion). MadGraph SUPPORTS two escape sentinels for this:
- `0.000001e-99` means "really 0 but do not restrict" → un-escaped to 0 at pipeline step 2457-2461.
- `9.999999e-1` means "really 1 but do not restrict" → un-escaped to 1.
`detect_identical_parameters` also skips these two sentinels (2724).
NOTE: NO shipped restrict card under `$MADGRAPH_INSTALL/models/*/restrict_*.dat` actually contains either sentinel (`grep` returns nothing). They are a supported mechanism for model authors, not exercised by any bundled SM/loop_sm/etc. card — so the un-escape and the 2724 skip are dormant for default workflows.

## Electron/muon Yukawa survey across all 9 variants
`grep -Hn '# yme' restrict_*.dat` (PDG 11, YUKAWA block, line 51) + same for ymm (13, line 52), Me (11, MASS line 20), MM (13, MASS line 21):
- ONLY `restrict_lepton_masses.dat` keeps yme/ymm/Me/MM nonzero (read magnitudes in that card).
- ALL 8 others (ckm, c_mass, default, no_b_mass, no_masses, no_tau_mass, no_widths, zeromass_ckm) keep `yme=ymm=Me=MM=0.0`.
So `import model sm-lepton_masses` is the ONLY shipped variant that keeps the e/μ Yukawa alive; a hand-authored `restrict_<tag>.dat` keeping `yme≠0` is equivalent. There is NO `sm-full` variant in 3.7.1. `sm-no_b_mass` is a common WRONG guess ("less restricted") — it only restores MB/ymb, still zeros yme, still removes the `e- e- h` vertex.

### Consequence: zeroed Yukawa ⇒ leptonic Higgs Yukawa process has zero diagrams
For full source-cited breakdown (H-ff + G0-ff + W-ff' vertices, exact file:line), see [removed-coupling-not-small.md](removed-coupling-not-small.md).
Because the default zeros `yme`, the `h > e+ e-` and `h > mu+ mu-` Yukawa couplings (GC_89/GC_93) go to zero and the vertices are REMOVED (not made small) — see remove-interactions.md "Removed ≠ small". Effects under default `sm`:
- `generate h > e+ e-` → `NoDiagramException : No amplitudes generated` (probe-confirmed). User expecting PDG BR ~5e-9 gets nothing.
- `h > l+ l-` with `l = e+ mu+ ta+` yields ONLY the τ subprocess; Hee/Hμμ generate zero diagrams.
- The param_card YUKAWA block of such a run lists only `ymb, ymt, ymtau` — the `yme`(11)/`ymm`(13) lines are ABSENT, not present-with-zero (restriction removed the external param ⇒ no card line written). [param_card line-presence is param-card's slice; here only as the downstream symptom.]
- Fix is model-load-time: `import model sm-lepton_masses` (or a custom restrict keeping yme≠0). A `set ye <val>` at the prompt or a param_card edit is moot — the param is gone (see remove-interactions.md).

## Naming convention (restrict_FOO.dat → X-FOO)

`import_ufo.py:get_path_restrict(model_name)` at lines 201-241 codifies the mapping.
When `model_name` contains a hyphen, `split[-1]` is the restrict tag (line 218);
the restrict file is resolved as `restrict_<tag>.dat` (line 220);
if tag == "full" the restriction is bypassed (line 223-224).
After import, the model name is appended with the tag: `model["name"] += '-' + restrict_name` (line 257).

Rule: `restrict_FOO.dat` in model X → import tag `X-FOO`. The tag IS the filename stem minus `restrict_` and `.dat`.
No transformation, no synonym, no alternate spelling. `restrict_lepton_masses.dat` → `sm-lepton_masses`.
`restrict_no_b_mass.dat` → `sm-no_b_mass`. Inventing a tag (e.g. `sm-no_lepton_masses` for
`restrict_lepton_masses.dat`) is a hallucination — the tag must match the file stem verbatim.

## Model-load-time constraint

Restriction runs at import time inside `import_model` → `restrict_model` (import_ufo.py:256-257, 7795).
It modifies `_curr_model` in memory: prunes vertices, converts 0/1 externals to internals, merges identical
couplings/masses/widths. The param_card is consumed AGAINST the restricted model; it cannot resurrect
a parameter that was removed during restriction. If a restrict card turns an external param into an
internal (or drops its coupling entirely), a later `set <param> <val>` or param_card edit is moot —
the param no longer exists in the operative model. Fix is always model-load-time: import the correct
restricted variant or supply a custom restrict card keeping the param alive.

## Caution
The "default" restriction (charm/e/mu massless, diagonal CKM) is silent — a user expecting massive charm or CKM mixing in plain `import model sm` gets neither. Use `sm-c_mass` / `sm-ckm`. Other models ship their own restrict sets (e.g. loop_sm mirrors SM; SMEFTatNLO has LO/NLO/NLO_no4q; MSSM_SLHA2 has default/no_b_mass/no_masses/no_tau_mass). `ls $MADGRAPH_INSTALL/models/<name>/restrict_*.dat` for the set.
