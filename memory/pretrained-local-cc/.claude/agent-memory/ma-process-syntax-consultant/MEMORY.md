## Recent lessons (FIFO, max 5)
- define-has-no-sub-keywords-maddm-correction: core do_define (madgraph_interface.py:3527) has ZERO keyword dispatch — 3545 `label = args[0]` takes the first token VERBATIM as the multiparticle name, `args[1:]` = particle-id list via extract_particle_ids. So `define darkmatter ~xd` / `define coannihilator ~xr` in core MG5 would create a multiparticle LITERALLY NAMED `darkmatter`/`coannihilator` (check_define 955 only blocks a label colliding with a model PARTICLE name; these don't) — NOT a MadDM "DM-candidate selection". `~xd`/`~xr` unknown in sm → hard `InvalidCmd("No particle ~xd in model")` at parse. `define darkmatter` is MadDM PLUGIN syntax (plugin overrides/adds do_define; plugin source absent = GAP), not core process-syntax. - parsers-diverge-by-path: "does syntax X work?" is PATH-DEPENDENT — there is no single shared tokenizer. extract_process leg loop, define/filter (extract_particle_ids), MadSpin (split_process_line/get_final_part), and the Switcher each re-implement spacing/@N/leading-digit/name-resolution and DIVERGE (probe: `2j` → 2 legs in generate, but `define`/filter reject it). Trigger: any "is X valid syntax" / "why does X work in generate but not define/MadSpin". Always qualify the answer by which command consumes the line. See multiple-independent-parsers.md.
- diagram-filter-vs-subdecay-forcing: `/ X` is a **diagram filter** (forbids X anywhere in diagrams); `, z > decay` is **sub-decay forcing** (forces Z as an explicit propagator with a decay). These are semantically opposite: `/ X` removes diagrams, `, z > decay` constrains the diagram topology to a specific chain. A user proposing `p p > z z / a a` to isolate ZZ-mediated contributions is wrong on two counts: (a) `/ a a` between intermediate and final states may be rejected (restrictions go after final states); (b) even if accepted, it only removes photon diagrams — it does NOT force Z bosons as explicit resonant propagators. The correct syntax for forcing ZZ topology with decays is `p p > z z, z > e+ e-, z > mu+ mu-`. Trigger: any "how do I isolate X-mediated contribution" / "is this process line right" question — state clearly that `/ X` is a diagram filter, not a topology constructor; route to diagram-filter-consultant for filter semantics and chain-decay-consultant for sub-decay forcing. Cross-ref: lead `process-line-scope-traps.md` §1. See extract-process-orchestration.md (parser: `/` parsed at 5007-5019, `,` routes at 3282).
- duplicate-check-needs-matching-@N: the do_add amplitude duplicate raise (madgraph_interface.py:3375-3378, "Duplicate process ... found") fires on `amp not in _curr_amps` = DICT equality (Amplitude has no __eq__). The `process` key carries `id`=proc_number=@N, which AUTO-INCREMENTS per add — so plain `generate X` + `add process X` (no @N) does NOT raise (probe: OK, n_amps=2); it raises ONLY with identical explicit `@N` on both. Trigger: any "does adding the same process twice error?" / duplicate-detection question — state the @N precondition, don't claim repeated processes always raise.
- tagged-message-depends-on-which-tag: "which tagged-particle error fires" is NOT just tree-vs-NLO — the photon check (5073-5076) runs INSIDE the per-token loop BEFORE leg construction, so an INITIAL NON-PHOTON tag raises "only initial photons can be tagged" AT TREE LEVEL (probe: `!u! u~ > e+ e-`), while final-state / initial-photon tags raise "tree mode does not handle tagged particles" (5231) which is reached LATER. Trigger: any "is 5076 reachable at LO?" / tagged-particle error-precedence question — distinguish initial-non-photon (5076 wins) from the rest (5231 wins); don't say 5076 is NLO-only. This refutes any claim that 5076 is "reachable only in non-tree LoopOption".
