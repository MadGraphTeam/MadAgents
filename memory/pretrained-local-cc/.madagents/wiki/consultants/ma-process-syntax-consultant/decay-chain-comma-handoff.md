# Decay-chain comma handoff — the parser entry boundary (v3.7.1)

`$MADGRAPH_INSTALL/madgraph/interface/madgraph_interface.py`. My slice owns the parser ENTRY: how a `,`-containing line is routed and what is validated before the chain-decay machinery runs, and that `extract_process` is re-invoked per segment. **The cascade assembly / mother-matching / `decay_chains` attachment is chain-decay slice's territory** — this page describes only what the entry layer guarantees and what it defers.

## Routing decision (do_add 3282)
- `do_add` (3232) does a flat substring test `if ',' in line:` (**3282**) — NOT paren-aware. ANY comma anywhere routes the whole line to `extract_decay_chain_process` (**5690** call). Else → `extract_process` (3310).
- **Incompatibility guard** (3283-3289): inside `do_add`, if `,` and (`[` or `]`) both present → `raise MadGraph5Error("The '[' and ']' syntax cannot be used in cunjunction with decay chains.")`. **CRITICAL precondition — this gate only fires for an EMPTY bracket `[]`, NOT a real `[QCD]`-style bracket.** The `do_add`/`do_generate` wrappers in `master_interface.py` (200, 260) call `extract_process_type` (162) FIRST; its `loopRE` (175) has a greedy `^(.*)` prefix that matches a comma/paren-bearing prefix, so a real bracket like `[QCD]` classifies as `('NLO',...)` and switches the interface to aMC@NLO / MadLoop (271-278) **before `MadGraphCmd.do_add` — where line 3283 lives — is ever entered**. An EMPTY `[]` has `orders=None` → `extract_process_type` returns `('tree',...)` (194-196) → stays on the MadGraph route → reaches 3283, where `'[' in line` is true and the "cunjunction" raise fires. (Interface-classification + switch is **nlo-syntax slice**'s territory; `master_interface.py` cited for the precondition only. The 3283 gate LOCATION/ownership is mine.)
  - **Probe-confirmed (v3.7.1, clean session):**
    - `p p > t t~ [] , t > b w+` → **3283 fires**: verbatim `str : The '[' and ']' syntax cannot be used in cunjunction with decay chains. ...` (empty bracket → tree route → MadGraph `do_add`).
    - `e+ e- > t t~ [QCD], t > b w+` → does **NOT** reach 3283. From default model state, MG5 auto-loads `loop_sm` (sm can't do `[QCD]`), the interface is already ML5/aMC@NLO, and the raise is `InvalidCmd : ML5 cannot yet decay a core process including loop corrections.` (`loop_interface.py:247`). **Model-state-independent**: with `import model loop_sm` preloaded, SAME `loop_interface.py:247` message — there is NO model state that produces "cunjunction" for a real-bracket + comma input.
- After `extract_decay_chain_process` returns, do_add re-checks decay-specific limits (3296-3308): `are_decays_perturbed()` → "Decay processes cannot be perturbed."; `decays_have_squared_orders()` or `squared_orders!={}` → "Decay processes cannot specify squared orders constraints."; `are_negative_orders_present()` → "Decay processes cannot include negative coupling orders constraints." (These inspect the assembled procdef — chain-decay slice owns the predicates; listed here as post-handoff gates.)

## Pre-handoff validation — check_process_format (1150), RECURSIVE over commas
Runs via `check_add (913) → check_generate (1146) → check_process_format`, BEFORE the `,` routing in do_add. For a decay-chain line it guarantees:
1. **Parenthesis balance** (1154-1155): `if process.count('(') != process.count(')')` → `InvalidCmd('Invalid Format, no balance between open and close parenthesis')`. Then `(`/`)` are replaced with spaces (1157) for the rest of the format check.
2. **Recursive per-subprocess split** (1160-1164): `subprocesses = process.split(',')`; if >1, recurse `check_process_format` on EACH subprocess and return. So the `>`-count check below is applied to every comma-segment independently.
3. **Per-segment `>` count** (1167-1168): `len(re.findall(r'>\D', process))` must be in `[1,2]` — so each decay segment must have exactly one (or two for nested `> >`) arrow. Empty piece (1174-1178) → `"... is a wrong process format. Please try again"`.
- **Probe-confirmed (v3.7.1, sm):** `e+ e- > , t > b w+` → format RAISE `"e+ e- > " is a wrong process format`. Unbalanced `e+ e- > t t~, ( t > b w+ ` → format RAISE `Invalid Format, no balance...`.

## extract_decay_chain_process re-calls extract_process PER SEGMENT (5661)
The chain splitter (5661) scans for the EARLIEST of comma / `)` (5683-5687 `min_index`), hands the substring BEFORE it to `extract_process` as the core (5690-5694), then loops over remaining comma segments (5698-5730), calling `extract_process` again on each `line[:min_index]` (5726) or `line` (5728). Nested `(...)` recurse into `extract_decay_chain_process` (5714).
- **So MY parser (`extract_process`) runs once per node of the chain tree, each on a bare `> `-containing substring.** A multiparticle in the core final state is expanded by `extract_process` at the core level; a multiparticle in a decay is expanded by the decay's own `extract_process` call — expansion is per-segment, not global.
- **Probe-confirmed (v3.7.1, sm) — instrumented `extract_process` to log each segment:**
  - `e+ e- > t t~, t > b w+, t~ > b~ w-` → segments `<<e+ e- > t t~>>`, `<< t > b w+>>`, `<< t~ > b~ w->>` (3 calls).
  - `e+ e- > t t~, (t > b w+, w+ > mu+ vm), t~ > b~ w-` → segments `<<e+ e- > t t~>>`, `<<t > b w+>>`, `<< w+ > mu+ vm>>`, `<< t~ > b~ w->>` (4 calls; the paren branch strips the `(` at 5712 before its segment).
- The `leftover` second return value is the splitter's recursion bookkeeping (the un-consumed tail). It is non-empty at the top level for a flat chain (`leftover=' t~ > b~ w-'`) because the `while` loop re-reads `line` from the last comma — this is chain-decay-slice internal; not a hazard for my parser, which only ever sees the per-segment substrings above.
- **`@N` in a chain** uses the VARIANT regex at 5666 `r"^(.+)@\s*(\d+)\s*((\w+\s*\<?=\s*\d+\s*)*)$"` (captures trailing overall orders too), distinct from extract_process's 4844 and split_process_line's 5486. The captured order string (group 3) is parsed into an `overall_orders` dict (5668-5679) and passed to the core `extract_process` (5690-5691), where it lands in the procdef's distinct **`'overall_orders'` key** (5347) — NOT the `'orders'` dict. Probe (v3.7.1, sm): `e+ e- > t t~, t > b w+ @3` → `id=3`; `... @3 QED=2` → `id=3`, `overall_orders={'QED':2}` while `orders={}`. (See multiple-independent-parsers.md idiom #2 — third divergent `@N` copy.)

## Defer-downstream hazards (entry layer passes, parser/assembly raises later)
`check_process_format` validates ONLY arrow structure + paren balance + non-empty pieces. It does NOT resolve particle names or check polarization placement inside a decay. Probe-confirmed (v3.7.1, sm):
- **Unknown decay particle**: `e+ e- > t t~ , t > zzz w+` → format **OK**, then `extract_decay_chain_process` → `InvalidCmd: No particle zzz in model` (raised by the per-segment `extract_process`, particle-name-resolution.md). The error is deferred from the entry gate to the segment parser.
- **`{pol}` on a chain core final**: `e+ e- > t t~ {T}, t > b w+` → format **OK**, then `extract_decay_chain_process` → bare `string index out of range` (a crash, not a clean InvalidCmd). Polarization-in-chains semantics belong to polarization + chain-decay slices; noted here only that the ENTRY gate does not catch it.
- **Empty core in a chain**: `e+ e- > , t > b w+` → format catches it (above), but if reached directly, `extract_decay_chain_process` → `'NoneType' object has no attribute 'get'` (the core `extract_process` returned None — see extract-process-orchestration.md implicit-None — and `.get('decay_chains')` crashes). The entry format gate is what protects the live `generate` path from this crash.

## Re-parse-helper survival (MadSpin/reweight path) — does a chain string survive intact?
The MadSpin/reweight helpers (madspin-reweight-parse-helpers.md) re-parse a process line independently. Probe-confirmed (v3.7.1, sm):
- **`split_process_line`** does NOT split on commas — it strips only `[NLO]`/`@N`/orders/filters. A decay-chain line survives in `core` VERBATIM: `split_process_line('e+ e- > t t~, t > b w+, t~ > b~ w-')` → `core='e+ e- > t t~, t > b w+, t~ > b~ w-'`, `opt=''`. Good for MadSpin (wants the whole chain).
- **`get_final_part`** recurses through the chain and returns the correct final-state pid SET, including through nested parens: `e+ e- > t t~, t > b w+, t~ > b~ w-` → `[-24,-5,5,24]`; `e+ e- > t t~, (t > b w+, w+ > mu+ vm)` → `[-13,-6,5,14]`. Strips `@N` and `{pol}` (probe: `e+ e- > t t~ @5` and `e+ e- > t{T} t~` both → `[-6,6]`).
- **DIVERGENCE / hazard**: these helpers DON'T run `check_process_format`, so a malformed chain that the live `generate` path rejects is silently MIS-parsed here, not raised. Probe: unbalanced `e+ e- > t t~, ( t > b w+ ` → `get_final_part` returns `[-6, 6]` (silently wrong — never sees the b/w+ decay), `split_process_line` returns the malformed line verbatim. So a syntax fix or validation added to the `extract_process`/`check_process_format` entry does NOT propagate to the MadSpin/reweight re-parse — predict skew (multiple-independent-parsers.md).
