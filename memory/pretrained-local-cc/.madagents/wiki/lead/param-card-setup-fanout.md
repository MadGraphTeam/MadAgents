# BSM/EFT parameter cards & parameter setup — declare → prune → rename → write → fill

A "set up / edit / understand the param_card for a BSM/EFT model" question fans across the model-load and card stages along a parameter's VALUE lifecycle. Same shape as `decay-widths-lifecycle` and `model-content-lifecycle` (an instance of `config-value-lifecycle-layers`): the operative value at a given `Block`/lhacode is whatever the LATEST stage wrote. This is the **value** analog of `model-content-lifecycle`'s **content** axis — the model-load stage carries two parallel lifecycle fan-outs (particle/vertex content; parameter values). For the EFT *physics* axis (NP power counting, `[...]` bracket interaction, online fetch) use `eft-smeft-fanout`; this page is the card-mechanics axis spanning ALL BSM families. Dispatch behaviour only; confirm one cited file:line before adopting a consultant page as evidence.

## Cross-cutting invariant
The param_card block/lhacode structure is a direct image of the model's `parameters.py` **external** params (one `Block` per `lhablock`, one line per `lhacode`), lowercased on write. A line exists in the card **iff** its UFO Parameter has `nature=='external'`; everything downstream only moves/zeroes/renames those lines, never invents one. So a value the user "set" that didn't take is almost always a line pruned upstream (dropped, not zeroed) or a name confusion (code-name vs card-key), not a card the run ignored.

## Stages

- **DECLARE (UFO `parameters.py`)** → `ma-ufo-consultant` `ufo-param-to-paramcard-chain.md` — card-membership predicate is exactly `Parameter.nature=='external'` (`import_ufo.py:2156-2164`): external → `ParamCardVariable(name,value,lhablock,lhacode,scale)`, internal (a formula) → excluded. External-needs-LHA invariant (`object_library.py:161-162`): an external param can NEVER lack lhablock/lhacode → "won't appear in card" means `nature=='internal'`, not "missing lhablock". `coupling_orders.py` carries NOTHING to the card (the LHA block named `DIM6` is a `parameters.py` Parameter, not a `CouplingOrder`). EFT operator representation → `ufo-smeft-eft-representation.md`; width DECAY-block → `ufo-width-declaration.md`.

- **PRUNE (restriction)** → `ma-restriction-consultant` `bsm-eft-param-card-value-fate.md` — value→fate table across three BSM/EFT families. A zeroed external can de-select directly (SMEFT Wilson coeff `==0` prunes the operator's vertices) OR via an extra hop (2HDM `lR7=0` → internal `l7` → coupling → prune). MSSM_SLHA2 mixing 0/1 entries are matrix STRUCTURE, not de-selectors — which is WHY MSSM is forced `keep_external=True` (via the explicit `elif model_name=='MSSM_SLHA2'` branch at `import_ufo.py:302-303`; the `mssm`-only raise at `:2398` is a separate safety check that never fires for `MSSM_SLHA2`). Magic-value escape (`0.000001e-99`→0, `9.999999e-1`→1) keeps a param free + numerically 0/1 while dodging every prune/merge and emitting no rule (no bundled card uses it). Mechanism pages: `smeft-restrict-operator-selection.md`, `parameter-fixing-and-merging.md`.

- **RENAME (`--noprefix` / `mdl_`)** → `ma-model-loader-consultant` `mdl-prefix-parameter-naming.md` — `--noprefix` drives two mechanisms (ALOHA routine names + model-parameter rename); fixed exclusion list `['as','mu_r','zero','aewm1','g']` (`base_objects.py:1658`). KEY for cards: the param_card is keyed by `lhablock`+`lhacode`, and the writer STRIPS `mdl_` from the comment (`write_param_card.py:246-247`) → **card bytes are identical under both prefix modes**. The "prefix breaks a hand-edited card" hazard is OVERSTATED: the toggle breaks names-in-CODE (`set mdl_cp` vs `set cp`, Fortran identifiers, by-name script/restrict refs), not card bytes. User-facing Wilson-coeff name in `display parameters`/`set <name>` is `mdl_<coeff>` by default.

- **WRITE (operative card)** → `ma-param-card-consultant` `operative-source-chain.md` (lineage UFO defaults → restriction → output-written → user edit → run-time read; latest governs; wrong-template trap) + `mssm-slha2-name-gating.md` + `data-model-classes.md`. Two card-mechanics traps: (1) the shipped MSSM is `MSSM_SLHA2` — native SLHA2 throughout; the SLHA1-conversion / `MG5_param.dat` machinery is DEAD for it (all three MSSM branches gate on `=='mssm'`/`startswith('mssm-')`; no shipped model matches; legacy `mssm` is retired, import errors → "replaced by MSSM_SLHA2"). (2) Custom-block CASING dichotomy: the fresh writer emits `Block <name>.lower()`, `ParamCard.__str__` emits `BLOCK <NAME>.upper()`; both load identically (name lowercased on read), so on-disk casing only marks which writer last touched the card. The SLHA1↔SLHA2 conversion routines remain reachable on demand via the card editor (`update to_slha1`/`to_slha2`), just never auto-invoked for `MSSM_SLHA2`.

- **FILL (DECAY block / AUTO)** → `ma-madwidth-consultant` `compute-widths-flow.md` — AUTO detection is card-driven and model-agnostic (no BSM branch). The FeynRules analytic 2-body shortcut is gated on the UFO shipping a non-empty `decays.py` (`all_decays`; gate at `import_ufo.py:426`, the no-attr `break` near `madgraph_interface.py:9871-9873`); typical BSM/EFT new-physics UFOs ship none, so every channel is integrated numerically via MadEvent (slower, same-in-principle). Full width lifecycle → `decay-widths-lifecycle`.

## EFT-specific card content
For Wilson-coefficient cards → `ma-eft-consultant` `eft-wilson-coeff-param-card-generation.md` + `eft-smeft-fanout`. Traps that bite EFT card edits:
- Block name is LOWERCASED in the card (`Block dim6` ≠ `lhablock='DIM6'`).
- Same block name, DIFFERENT lhacode→operator map across models (e.g. `DIM6` lhacode 2 = `ctp` in dim6top vs `cpDC` in SMEFTatNLO; SMEFTatNLO's `DIM6` block stops at a small max lhacode — read the block — so a lhacode valid in one model can be out-of-range in the other) — never carry a lhacode identification between EFT models.
- SMEFTatNLO `DIM6` lhacode 1 is Lambda (the cutoff SCALE — read its default in the `DIM6` block of `param_card.dat`), not an operator.
- Default EFT contribution is all-zero either way but for DIFFERENT reasons: dim6top ships all coeffs `0.` (no restrict card), SMEFTatNLO zeroes via `restrict_default` (the trap) — same end-state, different cause (so "is the default SM?" routes the same answer but a different mechanism per model).
- A restriction-pruned coeff line is DROPPED from the card (lhacode gaps); a hand-added pruned line is silently inert — fixable only by re-`output` with a keeping restriction, not a card edit (`smeft-wilson-coefficient-blocks.md`).

## Dispatch ordering
- "Set up the param_card for model X" → ufo (what's declared external) → restriction (what survives) → param-card (operative card + lineage); add eft for Wilson-coeff specifics, madwidth for AUTO widths.
- "I set value V at Block B / lhacode N but the run did Y" → walk the lifecycle backwards: is the line even IN the card (restriction prune ← ufo external?) → is it the right key (`mdl_` code-name vs card lhacode confusion → model-loader) → did a later stage overwrite it (operative-source-chain). Restriction-prune (a missing line) and name-confusion are the two most common answers; the run rarely "ignored" a present card line.
- "Why is the MSSM card SLHA1 / uses MG5_param.dat" → it isn't, for any shipped model (`MSSM_SLHA2` is native SLHA2); route to param-card `mssm-slha2-name-gating.md`.

## Verification discipline

**After any restriction change or param_card edit that is supposed to activate new couplings (EFT Wilson coefficients, BSM parameters, etc.), always regenerate and verify the matrix element actually contains the expected couplings.** The param_card line existing is necessary but not sufficient — the restriction may have pruned the coupling at model-load time, and a hand-edited card line is silently inert if the coupling was dropped. Concrete check: grep the generated `matrix1_orig.f` (or equivalent) for the expected coupling name (e.g. `GC_XXX`) or for the parameter name (e.g. `ctG`). If absent, the fix did not take — re-`output` with a keeping restriction, not a card edit. This is the behavioral gap that "it ran" does not cover: the run completes cleanly but with zero contribution from the intended new coupling.
