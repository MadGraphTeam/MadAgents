# What Codex can and cannot do

The mechanics a structural change must respect. A recommendation that assumes a behavior not listed here is not buildable on the Codex CLI — check it against this file before proposing it. (Established against Codex CLI 0.137 and the official Codex manual; items marked *verified* were confirmed by rendering the model-visible prompt with `codex debug prompt-input`. Version-specific, so re-confirm after a version bump.)

## Two effective levels — one dispatcher

There is one lead (the main session) and a flat set of roles. The lead spawns a role with `spawn_agent` and drives it with `wait_agent`, `send_input`, `resume_agent`, `close_agent`. A spawned role can itself spawn, so a middle tier is buildable; this harness keeps dispatch with the lead by choice. The `~6-8` fan-out cap is **prose in `lead-discipline.md`** and nothing else — the same as on Claude Code, which exposes no such setting. `.codex/config.toml` sets no cap; `[agents] max_threads` would be the key if one were ever wanted, and `.codex/config.toml` explains why there isn't.

**Codex's built-in guidance argues against delegating.** The `spawn_agent` tool description tells the model to spawn only when the user explicitly asks, to keep critical-path work local, and to call `wait_agent` sparingly. This system asks for the opposite — delegate the critical path, drain the wave — and that instruction lives in the lead's append. **A change that weakens or removes it does not merely lose a preference; it hands the turn back to a built-in that says "answer it yourself".** Treat the delegate-by-default language in `lead-discipline.md` as load-bearing.

## What loads, and where

- **`AGENTS.md`** auto-loads into **every** agent — lead and roles alike — as a *user*-role message, merged from the project root down to the working directory, capped by `project_doc_max_bytes` (32 KiB default). *(verified)* This is the only channel that puts the same content into every agent. **This layer deliberately ships none.** It is a *project*-scoped surface: it loads into a host project's own work too, so a discipline placed there would bind sessions that have nothing to do with MadGraph. The one `AGENTS.md` a deployment seeds is the environment description (where things are on this machine) — filesystem facts, not behaviour. **Do not recommend putting a discipline in `AGENTS.md`** — a cross-cutting discipline goes into every role that needs it (duplicated across roles, which is the accepted cost of isolation), and a lead-only discipline goes into `prompts/lead-discipline.md`.
- **Skill *descriptions*** (with each skill's path) reach every agent, injected at startup. **Skill *bodies* (`SKILL.md`) load only when an agent invokes that skill.** *(verified)* Mechanics buried in a skill body reach a role only if it invokes the skill; anything a role must always have in full cannot live in a skill body.
- **The lead's append** (`prompts/lead-discipline.md`, passed as `developer_instructions` at launch) and **the lead's slate** reach the lead only. It is *additive* — it splices into Codex's own developer message without displacing any of it. *(verified)* Roles never see it, because every role file defines its own `developer_instructions`, and a role's value replaces the parent's.
- **Each role** gets the `developer_instructions` of its own `.codex/agents/<name>.toml` — which here carries **both** its card and its slate.

## Memory

- Per-role slate: the region between `<!-- MADAGENTS-SLATE:BEGIN -->` and `<!-- MADAGENTS-SLATE:END -->` inside that role's `developer_instructions`. `developer_instructions` is a **required** field of every role file, and Codex applies the file as a configuration layer to every spawn of that role — so the slate is always loaded, with no tool call and no reliance on the agent choosing to read it. Only that role sees it.
- Lead slate: `.madagents/memory/lead/MEMORY.md`, concatenated onto the lead's append by the launcher at start-up. So a slate the lead writes is live from the **next session**, not mid-session.
- The wiki is **read on demand**, never auto-loaded.
- Slates are written through `.agents/skills/ma-wiki-write/scripts/write_slate.py`, never by hand. A malformed role file is dropped from the roster with no error — a consultant that has silently stopped existing.

## Dispatch

Each `spawn_agent` starts a **fresh, isolated** context — the role sees neither the lead's conversation nor its own prior dispatches. A role thread can be **resumed** (`resume_agent`), and it then retains its prior history. "Verify in clean context" means a fresh spawn, not a resume.

## Configuration gotchas that bite a structural change

- **`.codex/` is read only in a trusted project.** Untrusted, Codex ignores the whole project layer — including `.codex/agents/` — and the roster silently does not exist. Trust must be *recorded* in `$CODEX_HOME/config.toml`; a `-c projects.<path>.trust_level` override does not load the project layer (verified). The deployment records it; a recommendation must not assume it can be re-derived at runtime. To check whether roles actually loaded, ask whether `spawn_agent` has an `agent_type` parameter — no parameter means no roles.
- **A malformed `.codex/config.toml` takes the roster down with it.** The project layer is parsed as a whole, so one bad key there means no roles, reported (if at all) as a config error rather than as a missing roster.
- **The sandbox is the operator's choice, not the layer's.** The launcher passes no `--sandbox` flag, exactly as the Claude Code side pre-approves nothing. What that means in a container: Codex's sandbox is bubblewrap, bubblewrap cannot nest inside Apptainer's user namespace, and every sandboxed command fails with `bwrap: Can't bind mount /oldroot/ on /newroot/` — so a containerized session is started with `--sandbox danger-full-access` and the container is the boundary, exactly as for Claude Code. An install (no container) has no such conflict and keeps Codex's sandbox. Both are properties of the *deployment*: do not write either assumption into a card.
- **`developer_instructions` is ignored in a project-scoped `.codex/config.toml`** *(verified — and no warning is printed)*. It works from the user config, from the launcher's `-c`, and inside a role file. So "ship the lead's discipline in the project config" is **not buildable**; it has to come from the launcher.
- **`.codex/` and `.agents/` are read-only under the default `workspace-write` sandbox**, recursively — and a role's slate lives in `.codex/agents/<name>.toml`, so the *first* `/ma-wiki-write` asks for approval. That is intended, and it is one click rather than a standing cost: adding the command to the allow list makes Codex write a `prefix_rule` into `$CODEX_HOME/rules/default.rules`, which the deployment keeps across runs, so later runs skip it. This is why slates are written by a **script at a stable relative path** rather than by direct file edits — a path that changed per instance would need re-approving every time. Under `codex exec` an action needing fresh approval fails instead of asking, which is why an unattended run wants `--dangerously-bypass-approvals-and-sandbox`. **Do not recommend a permission profile or a `sandbox_mode` in `.codex/config.toml`** to remove that first prompt — pre-approving writes is a posture change that would make Codex the only part of the system granting anything up front, and it would apply to every install rather than to the machine whose owner clicked once. The renderer rejects such a config.
- **Per-role model, effort, and sandbox** are settable in the role file (`model`, `model_reasoning_effort`, `sandbox_mode`). This is a real capability worth using — a role pinned read-only is a stronger guarantee than an instruction not to write.

## What this means for a structural change

- A new always-on discipline → the **card half of every role it binds** (and `lead-discipline.md` if it binds the lead), not a skill body — a skill body never auto-loads, so a role gets it only if it invokes the skill. Not `AGENTS.md`: that is project-scoped and would bind the host's own sessions too. Scope the discipline per role, and expect to write it more than once; that duplication is the cost of an additive layer.
- A new role is reachable only through the lead's routing — it needs a clear `description` (the router) and a reason the lead would dispatch it.
- Removing a role removes a routing target the lead may rely on; changing a discipline that lives in N role files means changing all N, or the roster silently disagrees with itself.
- Every card edit is a TOML edit. Keep the file parseable and its `name` matching its filename, and never touch the marked slate region — that half belongs to the agent.
